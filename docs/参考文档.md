## 1 · 产品定位与设计原则

### 1.1 一句话定位

**ILB-1.1.1** ✅ ILB 是一个独立的世界书扩展：用户把设定写成一条条"条目"，ILB 在每次生成前判断**这一轮该出现哪几条**，只把这些条目的正文放进**这一次发出去的请求**里。

**ILB-1.1.2** ✅ ILB 的成败标准不是"功能有多少"，而是：**用户不读文档，也能在十分钟内让第一条设定按自己的意思出现。** 任何与这条冲突的设计，让步的是设计。

### 1.2 七条设计原则

**ILB-1.2.1** ✅ **只选条目，不改对话。** 注入内容只存在于单次出站请求的副本中，不写入 `chat`、不写入 `chatMetadata`、不进入后续轮次。这是机制保证，不是靠事后清理。

**ILB-1.2.2** ✅ **判定不进提示词。** 匹配规则、条件、算术只存在于运行时。注入的只有命中条目的 `content` 正文（宏替换后）。**用户永远不需要书写任何表达式语法**；所有条件都由界面控件生成结构化数据（见 ILB-6.2.3）。

**ILB-1.2.3** ✅ **失败即零注入，绝不中断生成。** 判定抛错、数据损坏、注入钩子时序异常——任何一种情况，生成管线必须照常继续，本轮不注入，错误写入诊断缓冲。**任何新功能的默认失败行为都是"不注入"。**

**ILB-1.2.4** 🔄 修订（v2.1.0）**数据只存自己的命名空间。** 不写入 SillyTavern 的 `worlds/`，不整份替换 `extension_settings`；ILB 的数据只落在 `extension_settings.independent_lorebook` 这一个命名空间里，且只能经 `BookRepository` 端口读写（见 ILB-3.1.2）。原文"数据只存自己的目录、不写入 `extension_settings` 作为主存储"已作废：前端扩展没有写文件的权限（决策 D-0012）。

**ILB-1.2.5** ✅ **导入只读、只复制、不删改。** 见 ILB-3.3.1。

**ILB-1.2.6** ✅ **每个界面元素都必须能被一句话解释，且这句话必须存在数据文件里。** 见 ILB-6.4。

**ILB-1.2.7** ✅ **可复现优先于随机。** 同样的输入必须得到同样的结果；随机必须显式开启，且使用可记录种子的随机源（SillyTavern 自带 `seedrandom`）。理由：用户报"这本书时灵时不灵"时，必须能复现。

### 1.3 与原生世界书的关系（对 v1 的修正）

**ILB-1.3.1** ✅ 运行时不调用 `world-info.js` 的内部函数、不读写其内存状态、不监听其触发事件。与原生世界书的运行时交互为零。

**ILB-1.3.2** ✅ **允许只读角色卡的绑定字段**（`characters[id].data.extensions.world`）用于"跟随角色卡自动切换书"。这是只读数据读取，不是内部逻辑调用。读取失败必须静默回退为手动选择，并在界面上显示"未能自动识别，已改为手动"。

> 修正说明：v1 的 A1 把这一条也禁了，退化为"每换一张卡手动选一次书"，与"低门槛"目标冲突。理由见 `docs/决策记录.md` 的 **D-0002**。

## 2 · 三层结构

```
┌───────────────────────────────────────────────┐
│  数据层 Data：只负责"存"和"搬"                  │
│  extension_settings.independent_lorebook          │
│  （books、settings、manualState、chatStates、导入日志）│
│  纯函数 CRUD；不知道有判定这回事                 │
└──────────────┬────────────────────────────────┘
               │ loadBook(bookId) → Book 快照
               │ （深拷贝，无引用泄漏）
┌──────────────▼────────────────────────────────┐
│  判定层 Eval：只负责"该出哪几条"                  │
│  evaluate(EvalRequest, Book) → ActivationResult │
│  纯函数；无 DOM、无 ST API、可脱离 ST 单测        │
└──────────────┬────────────────────────────────┘
               │ ActivationResult（含 diagnostics）
┌──────────────▼────────────────────────────────┐
│  注入层 Sink：只负责"把正文放进这一次请求"          │
│  InjectionSink 抽象 + 能力探测                   │
│  不修改 chat、不持久化                           │
└───────────────────────────────────────────────┘
```

**ILB-2.1** ✅ 依赖方向严格单向：注入层可以引用判定层的**类型**，但不得调用其判定函数；判定层只接收数据层的**返回值**，不得 import 数据层模块；数据层不知道另两层的存在。

**ILB-2.2** ✅ 层间只传两种纯数据：`EvalRequest` 与 `ActivationResult`（定义见 ILB-4.1.1、ILB-4.1.2）。任何其他形式的跨层调用都算违规。

**ILB-2.3** ✅ 一次生成的完整时序：

```
用户点发送
  → 注入层取快照 buildRequest()      （纯数据）
  → 数据层 loadBook()                （快照）
  → 判定层 evaluate()                （纯函数）
  → 注入层 sink.write(blocks)        （写副本，不写 chat）
  → 请求发出
  → 判定层产出的 stateUpdates 落盘    （仅时效状态，见 ILB-4.5）
```

> 注意：`stateUpdates` 是唯一允许"写"的东西，且只写 ILB 自己的状态文件，不进 chat。

**ILB-2.4** 🔄 修订（v2.1.1）**端口化（低耦合的硬约束）**：每一个外部依赖——宿主 API、存储、注入通道、模型调用、时间与随机源——都必须藏在一个**端口**后面（一份接口 + 一个默认实现）。上层只依赖端口，不得直接 import 宿主模块；**整个扩展只允许一个文件碰宿主代码**（`host.js`，位于扩展根目录）。它同时要提供宿主 API 的来源信息（`via`）和"请求落盘"的能力（`saveSettings`），因为"怎么和 SillyTavern 打交道"是唯一会随宿主版本变化的知识。

推论：

- 新增一个功能 = 新增一个端口实现，或向注册表追加一项，**不改动已有模块**。
- 端口必须能在没有宿主的环境里用假实现替换，否则它就不是端口，只是换了个名字的 if 分支。
- 任何模块被单独删掉，其余模块必须仍能加载（可以降级，但不能抛错）。

**ILB-2.5** ✅ **失败隔离**：任一模块抛错只能降级，不得让扩展整体停止工作。降级顺序固定为：该功能不可用 → 该书不出现在书架 → 本轮零注入 → 界面上写明原因。注册表里每个处理器独立 try/catch，一个处理器炸了不影响其他处理器。

## 3 · 数据层

### 3.1 目录布局

**ILB-3.1.1** 🔄 修订（v2.1.1）全部数据存放在**扩展自己的命名空间**内，绝不写入 SillyTavern 的 `worlds/`，也绝不写入 `chatMetadata` 或聊天正文。逻辑布局：

```
<ilb 命名空间>/
  books[]        一本世界书一条记录（整本整体读写）
  settings       全局设置
  manualState    手动开关（每本书一个布尔）
  chatStates     时效状态（每个聊天 × 每本书 × 每条目）
  importLog      导入记录，只追加，最多 50 条
```

> 原文中 `imports/<hash>` 一项已删除（D-0017：不留原件副本，原件即备份）。

**ILB-3.1.2** 🔄 修订（v2.1.1）**物理落地方式**：SillyTavern 的第三方前端扩展**没有服务端写文件权限**，因此上面的布局以"命名空间"而非"磁盘目录"落地——默认实现把上述五项序列化进 `extension_settings.independent_lorebook`；另外提供"整库导出为单个 JSON 文件"。

- 所有访问必须经 `BookRepository` 端口，**禁止任何模块直接读写 `extension_settings`**（这条是低耦合的硬约束，见 ILB-2.4）。
- **落盘是扩展的责任，不是宿主的**：只改内存里的 `extension_settings` 对象不会被自动保存，每次写操作后必须调用宿主的 `saveSettingsDebounced()`（经端口，失败不抛）。这一条原文写成"由宿主自身负责落盘"，是错的（D-0018）。
- 将来若出现可用的服务端存储，只替换端口实现，上层零改动。
- 理由见 `docs/决策记录.md` 的 **D-0012**、**D-0018**。

**ILB-3.1.3** 🔄 修订（v2.1.1）持久化只经宿主写入（`saveSettingsDebounced` 一类的去抖保存），且**每次写操作后都要叫一次**；禁止自行分片写盘、禁止在生成过程中同步写。整库导出使用单文件写出。生成路径上不允许出现任何写操作。

### 3.2 条目结构（schema v2）

**ILB-3.2.1** ✅ 书的顶层：

```jsonc
{
  "schema_version": 2,
  "book_id": "uuid",
  "name": "王城",
  "created_at": 0,
  "updated_at": 0,

  "activation": {              // 这本书什么时候算启用（见 ILB-3.5）
    "mode": "manual",          // always | character | manual
    "characters": [],          // mode = character 时生效：角色卡 id 或 name
    "manual": true             // mode = manual 时的手动开关
  },
  "pool": { "share": false },  // true = 即使本书未启用，条目也进入全局条目池

  "entries": [ /* Entry */ ]
}
```

**ILB-3.2.2** ✅ 条目（Entry）：

```jsonc
{
  "id": "uuid",              // 全局唯一，加载时强制前缀为 "<book_id>::<id>"
  "title": "王城·夜巡",        // 仅界面用，不参与匹配
  "content": "……",           // 唯一会被注入的正文（导入后不再被程序改写）
  "enabled": true,

  "always": false,           // true = 不判触发词，每轮都考虑（对应原生常驻）

  "trigger": {               // 什么时候出现
    "any":  [],              // 命中任一
    "all":  [],              // 全部命中
    "not":  [],              // 一个都不能出现
    "matchCase": false,      // 区分大小写
    "wholeWords": false,     // 整词匹配
    "regex": [{ "source": "", "flags": "i" }],
    "secondary": { "logic": "AND_ANY", "keys": [] }  // AND_ANY|AND_ALL|NOT_ANY|NOT_ALL
  },

  "scope": { "within": null },   // 只看最近 N 条消息（1..10），null = 用全局扫描深度

  "when": [],                // 条件卡片数组，空 = 无条件。结构见 ILB-4.4

  "group": null,             // 同组互斥
  "weight": 100,             // 越大越优先；同组择一用；预算排序用
  "probability": 100,        // 100 = 不掷骰
  "useProbability": false,   // 只有 true 时才真的掷骰

  "timed": { "sticky": 0, "cooldown": 0, "delay": 0 },   // 单位：消息条数

  "chain": { "participate": true },   // 是否参与连锁触发（见 ILB-4.6）

  "injection": {
    "position": "after_char",   // before_char | after_char | in_chat
    "depth": 4,                 // 仅 in_chat 有效，0 = 最后一条之后
    "role": "system"            // system | user | assistant
  },

  "_source": {                  // 导入溯源，见 ILB-3.3.6
    "book_file": null,
    "uid": null,
    "unknown": {}               // 无法识别的原生字段，原样暂存
  }
}
```

**ILB-3.2.3** ✅ `trigger`（何时出现）与 `group/weight/probability`（出现之后怎么筛）必须分开存放。判定顺序依赖这个分离，混在一起会导致概率和互斥在错误时机生效。

**ILB-3.2.4** ✅ `content` 一经导入不得被程序改写。任何"建议修改"都以**新条目**或**用户的显式确认**落地，不留隐式改写。

### 3.3 导入（原生世界书 → ILB）

**ILB-3.3.1** ✅ **信任三原则**：

1. 只读源文件，绝不删除、改写、移动 `worlds/` 下的任何文件；
2. **原件就是备份**：源文件本身不动，用户随时能在原生目录里找回原始版本；ILB 只在书里记录源文件名与源文件哈希（`_source.book_file`、`_source.source_hash`）用于幂等判定与"原件变了"提示，**不复制文件、不落任何盘**（前端扩展没有写文件权限，见 D-0017）；
3. 导入永不自动删除 ILB 中的已有条目，只做新增或按来源更新。

**ILB-3.3.2** ✅ 导入是一次性的格式转换，**不做运行时读取原生格式**。转换完成的瞬间起，ILB 与原生文件不再有关系。理由见 `docs/决策记录.md` 的 **D-0003**。

**ILB-3.3.3** ✅ 导入必须**幂等**：同一源文件重复导入，按源文件哈希 + `_source.uid` 配对，更新已有条目而不是新建一本。界面上必须显示"这是第 N 次导入，将更新 X 条、新增 Y 条、删除 0 条"。

**ILB-3.3.4** ✅ 字段映射见附录 A。**映射表中的每一行都必须有一条对应的测试**。

**ILB-3.3.5** ✅ 无法识别的字段一律原样存入 `_source.unknown`，不丢弃；导出时尽量还原。这让"导入再导出"尽可能接近原件，避免用户因为怕丢数据而不敢用。

**ILB-3.3.6** ✅ 每次导入在 `extension_settings.independent_lorebook.importLog` 里追加一条记录（时间、源文件名、源文件哈希、条目数、转换警告数），最多保留最近 50 条，超出时从最早的开始丢。同时把 `book_file` 与 `uid` 写进条目的 `_source`。导入日志写失败不得阻断导入。

**ILB-3.3.7** ✅ 转换警告必须在界面上可见、可逐条查看，不能只进 console。至少覆盖：

- `constant: true` 但 `key` 非空（脏数据，见 ILB-7.5）
- 位置为"作者注释前/后"（ILB 的位置枚举没有对应项，会降级为 `after_char`）
- 条目的 `scanDepth` 与全局不一致
- 正则无法编译
- 存在 `vectorized` 标记（v1 不支持语义匹配，该能力会丢失）

**ILB-3.3.8** ✅ 导出（ILB → 原生格式）为**可选功能**，但必须存在。存在理由是"可退出性"：用户要能随时把书带回原生世界书，这是让人敢投入的前提。

### 3.4 结构不变量

**ILB-3.4.1** ✅ 加载时校验以下不变量，校验失败的书标记为 `readonly` 并在界面提示，**不得丢弃原始文件**：

- `schema_version` 可识别
- `book_id` 唯一
- 条目 `id` 在书内唯一，加载后加 `<book_id>::` 前缀
- `weight`、`probability` 在合法范围
- `scope.within` ≤ 10
- `timed` 三项 ≥ 0

**ILB-3.4.2** ✅ 版本迁移在加载时**惰性执行**（读到旧版本 → 迁移到内存 → 下次写入时持久化）。迁移失败 → 该书 `readonly` + 提示，原件不覆盖。

### 3.5 多本书的启用与调用范围

**背景**：不同的世界书性质完全不同——有的是文风指导，有的是背景设定，有的是附加选项，有的是第三方书。原生世界书允许角色卡绑定若干本书，但它只解决了"启用"，没解决"书名下的条目能不能被别处的逻辑调用"。本节补上这一层。

**ILB-3.5.1** ✅ 每本书有两个**互相独立**的开关：

1. **启用方式** `activation.mode`：`always`（永远启用）/ `character`（跟随角色卡）/ `manual`（手动开）。回答"这本书这一轮要不要参与"。
2. **参与全局池** `pool.share`：回答"别处的规则能不能直接调用它的条目"。

两者不得合并成一个开关。合并会导致"我想让规则引用它的条目，但不想它整本自动注入"这个最常见的需求无法表达。

**ILB-3.5.2** ✅ `mode: "character"` 的判定顺序：

1. 只读角色卡的世界书绑定（ILB-1.3.2，读取本身不构成依赖）；
2. 绑定值与 `activation.characters` 或原生书文件名匹配 → 启用；
3. 读不到绑定（API 变动、卡片无绑定、群聊无主角色）→ **回退到 `manual`**，并在界面标注"未能读取角色卡绑定，已按手动处理"。

**ILB-3.5.3** ✅ 本轮条目池 = 「`activation` 判定通过的书的全部条目」∪「所有 `pool.share: true` 的书的条目」。第二条是"总条目池"的来源：一本书可以完全关闭、不自动注入，但把它放进池子里，让规则按需点名调用。

**ILB-3.5.4** ✅ 条目 id 全域唯一（`<book_id>::<id>`）。规则可以引用**池内任何条目**；引用了池外条目时，该规则本轮不成立，并在诊断里写明「它引用的《X》本轮未启用」。

> 这一条修订了 ILB-4.4.5（原定"只能引用同一本书内"）。放宽的理由：多书并存是常态，强行限制在同书内会让"文风书引用设定书"这种正当需求无处安放。

**ILB-3.5.5** ✅ 书架面板必须逐本显示：是否启用、**为什么**（永远启用 / 跟随角色卡 / 你手动关了 / 未启用）、本轮占用 token、是否参与全局池。四态必须能看到，否则用户永远搞不清"我的书为什么不生效"。

**ILB-3.5.6** ✅ 默认值：导入的书 `mode: "manual"`、`manual: true`、`pool.share: false`。理由：第一次导入后至少让人看一眼再决定；共享池默认关闭，避免第三方书里互相引用的条目在小上下文上把预算撑爆。

**ILB-3.5.7** ✅ 启用判定必须是纯函数 `resolveBooks(books, context)`，`context = { characterId, characterName, boundBooks: string[], manualState: Record<bookId, boolean> }`。**判定失败不得抛错**，只回退。

**ILB-3.5.8** ✅ 预留扩展点：允许注册额外的启用提供者 `BookActivationProvider = { id, test(book, ctx): true | false | null }`，`null` 表示"不表态"。内置只注册 `always` / `character` / `manual` 三种；"按情况启用"（按标签、按在场角色、按时段等）作为将来可插入的第四类，本版本不实现（见附录 D 的 **ILB-D4**）。

### 3.6 导入策略与"不会越导越多"（v0.3.0 新增）

**背景**：用户反馈两件具体的事。一是媒体上的世界书很多，一本本点太麻烦；二是导入后不确定原件里的开/关状态、以及重复导入会不会产生副本。本节把这两件事定死。

**ILB-3.6.1** ✅ 导入时的开/关处理有四个策略 `importEnabledPolicy`：`ask`（每次问）/ `keep`（保留原件）/ `on`（一律启用）/ `off`（一律停用）。默认 `ask`。

**ILB-3.6.2** ✅ `ask` 不是"随便挑一个"：它要求界面在导入前弹出选择，**不允许**静默按 `keep` 或 `on` 处理。理由：用户明确说过"没设置就问我"，静默处理等于把问题藏起来。

**ILB-3.6.3** ✅ 判断"这本书是不是已经导入过"只能按 `_source.book_file`（来源文件名），**不能按书名**。书名可以重名，用户也会改书名。纯函数 `planBatchImport(files, books, { includeExisting })` 负责出计划：`{ queue, skipped, total }`。

**ILB-3.6.4** ✅ "一键导入全部"默认跳过已导入的书（`batchImportIncludeExisting: false`）。想整批重导，必须在设置里显式打开"也包含已经导入过的书"，或在导入弹窗里勾选。

**ILB-3.6.5** ✅ 每次导入结束必须报告四个数：**更新 / 新增 / 保留 / 冲突**，并写进导入记录。只说"导入成功"是不够的——用户无法判断自己的改动有没有被覆盖。

**ILB-3.6.6** ✅ 元信息必须落盘，否则"原件变了"和"我改过"这两件事无法区分：

| 位置 | 字段 | 用途 |
| --- | --- | --- |
| 书 `_source` | `book_file` | 认来源、判重复 |
| 书 `_source` | `source_hash` | 原件指纹，判断原件是否变过 |
| 书 `_source` | `imported_at` / `import_count` | 上次导入时间、第几次导入 |
| 条目 `_source` | `uid` | 与原件条目的对应关系 |
| 条目 `_source` | `content_hash` | 用户是否手改过正文 |

**ILB-3.6.7** ✅ **原件即备份**：不复制原生文件、不在扩展目录另存一份。只记指纹。理由见 D-0017——整份原件塞进 `extension_settings` 会让每次保存都序列化几百 KB。

**ILB-3.6.8** ✅ 提供"检查原件"动作：逐本比对当前指纹与记录的指纹，回答"没变 / 变过了 / 读不到 / 以前没存指纹"。这个动作**只读**，不自动重导。

## 4 · 判定层

### 4.1 契约

**ILB-4.1.1** ✅ 输入：

```ts
interface EvalRequest {
  messages: { role: string; content: string }[];   // 时间正序，快照副本
  userInput: string;          // 本轮用户消息（若尚不存在则为空串）
  characterDescription: string;
  personaDescription: string;
  scanDepth: number;          // ILB 自己的设置，默认 3
  history: { entryId: string; lastActiveAt: number; activeSince: number }[];
  vars: Record<string, string | number>;   // ILB 自己的变量命名空间
  trigger: "normal" | "continue" | "regenerate" | "swipe";
  seed: number;               // 随机种子，便于复现
}
```

**ILB-4.1.2** ✅ 输出：

```ts
interface ActivationResult {
  activated: {
    entryId: string;
    content: string;          // 已做过宏替换
    injection: { position: string; depth: number; role: string };
    weight: number;
  }[];
  stateUpdates: { entryId: string; lastActiveAt: number; activeSince: number }[];
  diagnostics: {
    entryId: string;
    passed: boolean;
    reason: string;           // 人话，直接展示给用户
    stage: "trigger" | "when" | "timed" | "probability" | "group" | "budget" | "chain";
    estimatedTokens?: number;
  }[];
  basedOnMessageCount: number;
}
```

**ILB-4.1.3** ✅ 判定层不得接收 `chat` 数组引用，只接收快照副本。`messages` 的字符串可以直接复制（字符串不可变），数组必须新建。

**ILB-4.1.4** ✅ `diagnostics` 是产品功能，不是调试附属品。**每一条"没出现"的条目，都必须能回答"为什么没出现"。**

**ILB-4.1.5** ✅ 除上表字段外，`ActivationResult` 还带三个**只给界面看**的附加字段：`budget: { limit, used, dropped: string[] }`、`books: { active, inactive, reasons, warnings }`、`poolSize: number`。它们不参与判定，注入层不得读取；删掉它们也不应改变注入结果。理由：诊断面板要回答"为什么没出现"，而"预算挤掉"与"这本书这一轮不在场"是最常见的两个答案，不该让界面自己重算一遍（重算就可能和判定层算出不同的数）。

### 4.2 固定执行顺序

**ILB-4.2.1** ✅ 顺序不可重排：

```
0. 解析活跃书集合与条目池（ILB-3.5）：resolveBooks → 本轮候选条目
1. 组装基础文本 = 最近 scanDepth 条消息 + userInput
2. 第 0 层：对 enabled 条目判 trigger
   （always = true 的条目跳过此步直接通过）
3. 对通过者判 when（条件卡片）
4. 对通过者判 timed（delay / cooldown / sticky）
5. 连锁循环（见 ILB-4.6），最多 maxChainDepth 层
6. 对所有通过者判 probability（仅 useProbability = true 的条目）
7. 同组择一：同 group 内按 weight 降序取第一条
8. 排序：weight 降序 → 用户排序位次 → entryId 字典序
9. 预算截断：条目为原子单位，整条进或整条不进
10. 输出 ActivationResult + diagnostics
```

> 第 8 步的三级排序是硬要求。只按 weight 排序时，同权重条目的相对顺序在不同次运行可能不同，会导致注入块的内容顺序变化，进而失效提示词缓存（见 ILB-7.11）。

### 4.3 触发的用户语言

**ILB-4.3.1** ✅ 界面上不得出现 `AND_ANY`、`selectiveLogic` 这类词。对照表：

| 存储值 | 界面文字 |
|---|---|
| `any` 非空 | 「说到其中任意一个词」 |
| `all` 非空 | 「这些词全都要出现」 |
| `not` 非空 | 「这些词一个都不能出现」 |
| `AND_ANY` | 「再加上第二组里至少一个」 |
| `AND_ALL` | 「再加上第二组里的全部」 |
| `NOT_ANY` | 「第二组一个都不能出现」 |
| `NOT_ALL` | 「第二组不能全部出现」 |
| `always: true` | 「永远都在」 |

> 理由：原生世界书的二级键几乎没人用，不是因为它没用，而是因为它叫 `AND_ANY` 且藏在二级菜单里。能力没问题，命名杀死了它。

### 4.4 条件卡片（替代 v1 的表达式语言）

**ILB-4.4.1** ✅ v1 的"算术与条件表达式 AST（含 `+ - * / == !=` 等）"**已废弃**（⛔ 原 v1 §4.3 表达式部分）。用户不写语法。替代为下面 **三种卡片 + 两种连接词**。

**ILB-4.4.2** ✅ 卡片类型固定为三种，不得扩展（扩展需走决策记录）：

```jsonc
// ① 最近几句话里说到
{ "type": "contains", "within": 5, "text": "王城", "negate": false }

// ② 某条已经出现
{ "type": "activated", "entryId": "uuid" }

// ③ 变量比较
{ "type": "var", "name": "声望", "op": ">=", "value": 50 }
```

**ILB-4.4.3** ✅ 组合只有两种：

```jsonc
{ "type": "all", "of": [ /* 卡片 */ ] }   // 界面上叫「并且」
{ "type": "any", "of": [ /* 卡片 */ ] }   // 界面上叫「或者」
```

**ILB-4.4.4** ✅ `when` 数组本身语义为「并且」。空数组 = 无条件。

**ILB-4.4.5** 🔄 修订（v2.1.0）`activated` 卡片可以引用**本轮条目池内**的任何条目（含其他书的条目，见 ILB-3.5.4）；引用了池外条目时卡片不成立，并在诊断中写明原因。"是否已激活"仍指本轮**已确定要注入**，不含因预算被挤掉的条目。

**ILB-4.4.6** ✅ 卡片必须在界面上以"一句话能读完"的形式呈现，例如「最近 5 条里提到『王城』」。任何会渲染出嵌套超过两层的组合，界面应折叠为摘要行并提供展开。

### 4.5 时效

**ILB-4.5.1** ✅ 条目可设置三项时效（单位：消息条数，0 = 关闭）：

- `delay`：至少距上次触发 N 条之后才允许出现
- `cooldown`：触发后 N 条内不再出现
- `sticky`：触发后强制持续 N 条

**ILB-4.5.2** 🔄 修订（v2.1.1）时效状态按「书 × 聊天」存放在 `extension_settings.independent_lorebook.chatStates[<聊天>]`，不进 `chatMetadata`，不进 chat 正文。

**ILB-4.5.3** ✅ 时效判定属于判定层，但状态从 `EvalRequest.history` 传入、由 `ActivationResult.stateUpdates` 传出。判定层本身仍然无状态。

**ILB-4.5.4** ✅ 切换聊天 / 分支 / 删除消息时，状态以"消息条数"为基准自动失效，不做补偿计算。

### 4.6 连锁触发（涌现机制）

**ILB-4.6.1** ✅ 定义：一条条目被确定注入后，**它的正文里出现的词，可以继续触发其他条目**。这是"基础功能涌现复杂功能"的主要机制。理由见 `docs/决策记录.md` 的 **D-0005**。

**ILB-4.6.2** ✅ 连锁的匹配文本按层累积：第 k 层扫描的文本 = 基础文本 + 前 k−1 层已确定注入的 `content` 之和。

**ILB-4.6.3** ✅ 约束：

- 层数上限 `maxChainDepth` 默认 3，可调范围 0–5；0 = 关闭连锁
- `chain.participate: false` 的条目**不会被连锁带出**（但仍可被基础文本触发）
- 同一条目在一轮内只能被激活一次（防环）
- 连锁命中的条目**不进入第 0 层**，其 `when` 卡片在下一层重新求值
- 连锁只在 `trigger` 上生效，不在 `when` 上递归

**ILB-4.6.4** ✅ 导入的条目默认 `chain.participate: false`。理由：第三方书常有互引，直接开启容易在小上下文上把预算撑爆；用户可一键全开。

**ILB-4.6.5** ✅ 连锁必须留下诊断：界面上能展开看到"因《王城》提到『国王』而带出《国王》"。

### 4.7 预算

**ILB-4.7.1** ✅ 预算为 ILB 自有设置：`budget = min(上下文长度 × 0.15, 2000)`，可调。

**ILB-4.7.2** ✅ 截断以条目为原子单位：放不下就整条跳过，**不截断正文**。理由：截断正文会产生半句话，比不注入更糟。

**ILB-4.7.3** ✅ token 估算在同步路径上使用字符估算（CJK 按 `chars/3.5`，拉丁按 `chars/4`，混合按字符类别加权）；精确值由异步 tokenizer 在生成后回填进诊断，仅用于界面显示。

**ILB-4.7.4** ✅ 被预算挤掉的条目必须在生成后以轻量提示可见（如"本轮注入 3 条，因预算跳过 1 条"）。

### 4.8 纯函数与测试要求

**ILB-4.8.1** ✅ 判定层必须能脱离 SillyTavern 单测。所有输入都是纯数据，可直接构造。

**ILB-4.8.2** ✅ 测试至少覆盖：

| 用例 | 期望 |
|---|---|
| 空条目 / 空输入 | 零注入、不抛错 |
| 单关键词命中 | 注入 1 条 |
| `all` 缺一个词 | 不注入 |
| `not` 命中 | 不注入 |
| `matchCase` / `wholeWords` | 边界行为与原生一致 |
| regex 边界（空串、超长串） | 不抛错、有时间预算 |
| `useProbability: false` + `probability: 50` | 视为 100 |
| 同组三条同时命中 | 只出 weight 最高 |
| 同组两条同 weight | 按用户排序位次，稳定 |
| 预算不足 | 整条跳过，不截断 |
| 连锁 3 层 | 链式带出，第 4 层不再带出 |
| 连锁成环 A↔B | 各出一次后停止 |
| `delay` / `cooldown` / `sticky` | 状态推进正确 |
| 相同 `seed` 两次调用 | 结果字节级一致 |

### 4.9 "试一句"：把判定过程露出来（v0.3.0 新增）

**背景**：用户问"通过逻辑判定来选择是否触发的功能在哪里，我没看见"。问题的根源不是功能缺失，而是**判定结果不可见**：用户在界面上填了触发词，却没有任何地方能立刻告诉他"这句话会不会让它出现"。

**ILB-4.9.1** ✅ 新增纯函数 `previewEntry(entry, options)`，`options = { text, activated[], vars, messageCount, state: { lastActiveAt, activeSince } }`，返回 `{ passed, reason, steps: [{ stage, passed, reason }] }`。

**ILB-4.9.2** ✅ 它**必须复用** `evalTrigger` 与 `evalWhenArray`，不得另写一套判断。理由：两套实现必然漂移，最后"试一句说会出现、实际却不出现"，比没有这个功能更糟。

**ILB-4.9.3** ✅ 判定范围只到"条件"为止，顺序为 `enabled → timed → always → trigger → when`。**不做**概率、同组、预算、连锁、状态写回。理由：那几项依赖真实的一轮对话（同组要看对手是谁，预算要看上下文长度），假装能预演等于给错答案。

**ILB-4.9.4** ✅ 结果必须逐步返回 `steps`，界面据此显示"卡在哪一步"，而不是只给一个"会/不会"。

**ILB-4.9.5** ✅ 界面上每条规则都要有"试一句"入口；编辑器里也要有，且用的是**当前正在编辑的值**（未保存也能试），不是已保存的旧值。

### 4.10 判定流程（v0.4.0 新增）

**背景**：用户要求判定不要"以预设的方式展现"，而要像可视化编程 / 模块化编程 / 游戏引擎蓝图那样，由用户从上往下自己搭：检测 → 比较 → 成立就计算 / 添加 / 定义，不成立也由用户决定接下来做什么。同时明确要求：**新建或导入的书里默认没有任何流程**，此时完全走原生那套（注入位置、注入身份、权重、概率、关键词触发）。

**ILB-4.10.1** ✅ 流程 = 一棵**节点树**，不是画布。节点种类固定为八个：

| kind | 中文 | 作用 | 是否分叉 |
| --- | --- | --- | --- |
| `test` | 检测 | 判断一条条件（包含某词/正则/另一条已出现/消息条数/变量有值） | 是 |
| `judge` | 判定 | 把 2–8 条条件按「全部满足」或「任一满足」合并 | 是 |
| `compare` | 比较 | 两个操作数比较（变量 / 数字 / 文本） | 是 |
| `define` | 定义 | 给变量赋值 | 否 |
| `calc` | 计算 | 用两个值算出第三个值存进变量；运算符选 `=` 时是直接赋值 | 否 |
| `add` | 添加 | 往这条规则的正文后面追加一段 | 否 |
| `pass` | 通过（结束） | 立刻结束整条流程，这条规则出现 | 否 |
| `fail` | 不通过（结束） | 立刻结束整条流程，这条规则不出现 | 否 |

**ILB-4.10.2** ✅ **空流程必须完全等于原生行为**。判定的入口处先看 `hasFlow(entry)`：没有节点就一个字都不改，直接放行。这条是硬约束——它是"低门槛"承诺的兑现方式：不想用流程的人，永远不会被流程影响。

**ILB-4.10.3** ✅ 执行顺序：`enabled → timed → 触发词 → when 卡片 → 流程 → 概率 → 同组 → 排序 → 预算`。流程**追加**在关键词与条件之后，不替换它们（除了 `mode: "only"`，见 4.10.7）。

**ILB-4.10.4** ✅ 分叉语义：
- 判断成立 → 走 `then`；`then` 为空 → **继续往下**（"成立时不用特别做什么"）。
- 判断不成立 → 走 `else`；`else` 为空 → **整条流程判为不通过**，这条规则不出现。

第二条容易让人意外，但反过来（默认继续）会让"我明明写了判断，它却照样出现"，更难解释。规格选"留空 = 不出现"，并在界面上把这句话直接印在「不成立时」那一块里。

**ILB-4.10.5** ✅ 变量作用域：流程里的 `define` / `calc` 只写入**本条规则本次执行**的局部变量表，不写回全局、不影响别的规则、不落盘。理由：跨规则共享变量需要一套"谁先谁后"的约定，那会把简单的事情变复杂；等真的有人需要时再加。

**ILB-4.10.6** ✅ `add` 产生的文本拼在这条规则正文之后（换行分隔），并**计入预算**——预算算的是最终要注入的字符串，不是原始正文。这条防止"正文很短、追加一大段"绕过预算。

**ILB-4.10.7** ✅ `logic.mode` 只有两个值：
- `and`（默认）：关键词满足后，再走流程。
- `only`：关键词不参与判定，完全由流程决定。此时触发词仍会被保存，但**不参与**判定——界面上必须写明这一点。

**ILB-4.10.8** ✅ 上限：`MAX_NODES = 80`（单层最多 80 个节点）、`MAX_DEPTH = 8`（分支嵌套层数）、`MAX_STEPS = 200`（一次执行最多走 200 步）。超出的节点在归一化时被丢弃，超出的执行被终止并给出原因。理由：用户可能写出环（虽然树形结构本不该有环），也可能从别处导入奇怪的 JSON；有上限就不会把浏览器卡死。

**ILB-4.10.9** ✅ 流程必须活在 `core/flow.js` 里，是**纯函数**：不 import 宿主、不碰 DOM、不读存档。它的条件判定与 `evalCondition`（when 卡片）是两套词汇：前者面向"搭流程"，后者面向"填一张卡片"，两者语义相近但不共用一个函数，以免为了复用把界面语言绑死。

**ILB-4.10.10** ✅ "试一句"必须覆盖流程：流程的每一步都以 `stage: "logic"` 追加进 `steps`，让人看到"走进去、在哪一步被拦下"。

**ILB-4.10.11** ✅ 流程不允许做任何外部副作用：不发请求、不写状态、不改别的规则。它只能读快照、写自己的局部变量、产出追加文本。

### 4.11 触发来源、等候模式与楼层条件（v0.9.0 新增）

**4.11.1 来源**：条目与独立逻辑的 `trigger` 都带 `source`，取 `both`（默认）/`user`/`ai`。判定时按来源拼文本：`user` 只看用户消息（并总把本轮 `userInput` 算进去），`ai` 只看 AI 消息，`both` 与旧版一致。

**4.11.2 等候模式**：条目 `wait: true` 时不参加自动触发，只等流程里「激活条目」或「调用逻辑」点名；没被点名就永远不出现，诊断里会写"等候模式：不会自己出现，只等逻辑点名"。适合"只作为某条逻辑的下半段"的条目。

**4.11.3 楼层条件**：条件卡片新增 `type: 'messages'`，字段 `count`（整数）与 `negate`。人话是"现在至少第 N 条消息"或"现在还没到第 N 条"。计数用 `messages.length`（含本轮用户输入）；**AI 回复次数**用同样的条件配合 `trigger.source = 'ai'` 观察，不单独设变量。

**4.11.4 兜底**：消息没有 `role` 时按奇偶推测（用户在前、AI 在后）。这是给残缺聊天记录的容错，不保证准确。

### 4.12 独立逻辑（v0.9.0 新增）

**4.12.1 位置**：逻辑挂在书里 `book.logic[]`，`id` 形如 `<bookId>::L::<localId>`；字段 `name / enabled / trigger / scope / when / flow / output / call / ui`。

**4.12.2 自触发**：逻辑自己看触发词，**不需要先命中一条世界书条目**——一本只有逻辑、没有条目的书也能工作（`tests/logic-demo.mjs` 第一段验收）。没写触发词的逻辑不自动跑，只等「调用逻辑」或「激活条目」点名。

**4.12.3 输出**：`output.text` 与流程里「说一句」的文字合成一条伪条目，参与权重、分组与预算；被「调用逻辑」叫来时**不单独注入**，正文并进调用方。

**4.12.4 预算与去重**：每轮最多跑 `logicMaxPerTurn` 条（默认 20，设置页可调）；同一条逻辑一轮只跑一次；逻辑互相调用最多 5 层，超出显性失败。

**4.12.5 边界**：逻辑不参加条目关键词池，也**没有 group / timed / probability 字段**——避免两套语义各写一半。需要这些行为，用流程节点表达。

### 4.13 跳转与调用逻辑（v0.9.0 新增）

**4.13.1 跳转**：`kind: 'goto'`，`target` 是节点 id，`max` 默认 20（1–1000），`onLimit` 为 `stop`（终止）或 `continue`（从当前节点下一条继续）。计数按"跳到该节点"的次数算。

**4.13.2 允许往回跳**：不做"只能向前"的功能限制（用户拍板，m03835）；复用片段优先，用次数上限兜住死循环。整条流程仍受 `MAX_STEPS` 保护。

**4.13.3 目标不存在**：显性失败——"跳转目标不存在：id（可能已被删掉）"。

**4.13.4 调用逻辑**：`kind: 'call'`，`logicId` 指向一条独立逻辑；跑完把它的 `writes / extra / activations` 合并进调用方。被调逻辑 `passed === false` 会让调用方整条流程不通过。

**4.13.5 复制粘贴**：编辑器内的复制缓冲只在本次打开期间有效；粘贴会给节点与条件换新 id，两棵子树互不影响。跨书导入逻辑时，「跳转」目标 id 会按导入映射自动改写。

### 4.14 AI 调用逻辑（v0.9.0 新增，默认关闭）

**4.14.1 语法**：AI 正文里写 `[[ILB:名字(参数1,参数2)]]`，名字可以是逻辑的 `name` 或 `localId`；只有 `call.exposed === true` 的逻辑才可被调用。

**4.14.2 扫描与上限**：只看最近 `aiCallScan` 条 AI 消息（默认 3，1–50）；每轮最多执行 `aiCallMaxPerTurn` 次（默认 3，0–10）；同一段里同名同参只算一次；参数最多 8 个。**幂等**：每条 AI 消息里的每个调用只执行一次，处理过的 key 记在聊天变量 `__ilbCallsSeen` 里，重画/编辑/刷新导致的重放不会再执行第二遍。

**4.14.3 参数**：按 `call.params` 的顺序临时绑定成变量，跑完还原；它写出的值照常进"待写列表"，由 pipeline 落盘。

**4.14.4 权限边界**：AI **只能改聊天变量**（数字、文本），改不了 SillyTavern、扩展设置或书本身；扩展的宿主 API 不在调用作用域里。这是"对话工具不是 agent"的硬边界（D-0046）。

**4.14.5 失败必须出声**：没开放、超过次数、执行失败都写诊断（`stage: 'call'`）并进 `aiCalls` 记录，界面上看得到。

**4.14.6 默认值**：`aiCallsEnabled = false`。关着的时候 AI 写了调用也只是一段普通文字。

### 4.16 随机数节点（v0.10.0 新增）

**4.16.1 为什么要种子**：状态必须能从聊天记录重放出来。如果随机数直接取 `Math.random()`，同一条消息重画两次会得到不同的数，账本对不上；所以默认"按楼层取种子"。

**4.16.2 种子怎么来**：`seed = <chatId>:<当前消息序号>:<节点 id>`，经 `fnv1a` 映射到 [0,1)。同一条消息、同一份流程重画多少次都一样；下一楼才换。种子在 `core/evaluate.js` 里算一次，随 `ctx.seed` 传给 `evaluateFlow`。

**4.16.3 范围**：`min / max` 必须是数字，`max < min` 时按 `min` 算；`integer`（默认 true）决定取整还是取小数。结果写进 `node.target` 指定的变量。

**4.16.4 落盘**：默认"只本轮有效"（和「计算」旧行为一致）；勾「存进聊天」才进待写列表，跨轮保留。想"每轮重掷"就**不勾**，靠变量本来就会丢这件事实现。

**4.16.5 程序位置**：`makeNode('random')`、`normalizeNode`、`runNode`、`describeNode`、`core/flow.js`；界面在 `ui/flow-editor.js`。

### 4.17 元触发器（v0.10.0 新增）

**4.17.1 为什么要有**：初始化逻辑如果用普通触发词，要么永远等不到词，要么每次都触发；"每轮都跑 + 变量判定"才能表达"第一次进来时初始化一次"。

**4.17.2 四个值**：`none`（默认，老行为，看触发词）、`always`（每轮都跑，不看触发词）、`on_ai`（最后一条是 AI 回复时跑）、`on_user`（有用户输入或在用户发言回合跑）。写错的值一律回落到 `none`。

**4.17.3 与触发词的关系**：元触发器优先。`always` 时触发词、来源、排除词都不看；`on_ai / on_user` 时先过元触发器，再照常看触发词（没有触发词就不跑）。"等候模式"条目不受元触发器影响——它只等逻辑点名。

**4.17.4 幂等**：`always` 会在每次刷新/重画时跑，所以它的流程里不要写"每次都会加一次"的动作；要只做一次，用变量判断（例如 `未初始化 = 1` → 初始化 → 置 0）。这是用户侧要理解的一条纪律。

**4.17.5 程序位置**：`core/model.js` `normalizeTrigger` 的 `meta` 字段；`core/evaluate.js` 在独立逻辑与条目触发前判断；界面对应在「什么时候跑」下拉。

### 4.18 对外接口（v0.11.0 新增；v0.12.0 升到接口 1.1，ILB-4.18.1–4.18.12）

**4.18.1 只暴露一层**：别的扩展/脚本只许用 `window.ILB.api`，不许直接读 `repository / pipeline / 书的字段结构`；那三样是内部实现，随版本改。接口代码在 `runtime/api.js`，契约文档在 `docs/UI扩展接口.md`。

**4.18.2 五个入口**：`snapshot()`（只读快照）、`set(name,value)` / `remove(name)`（写聊天变量）、`call(nameOrId,args,opts)`（跑已启用的独立逻辑）、`subscribe(fn)`（变化通知，同时发 `document` 的 `ilb:change`）。另有 `version`、`caps`、`describe()`、`ui.openPanel(tab)`、`ui.close()`、`notify(reason)`。

**4.18.3 边界**：只写聊天变量，不改 SillyTavern 设置、不改扩展设置、不改书；`call` 不参与注入预算与排序；失败一律 `{ ok:false, outcome, reason }`，不把异常抛进调用方的事件循环。

**4.18.4 版本策略**：契约版本 `API_VERSION`（现 `1.1`）与扩展版本分开；加字段/加可选参数升小版本，改语义/删方法升大版本并保留一个发布周期的兼容层。`caps` 数组是给调用方做特性判断用的，比版本字符串稳。

**4.18.5 加载顺序**：谁先加载不确定，所以 ILB 启动时发 `ilb:ready`；拿不到 `window.ILB.api` 的扩展应降级为"不显示"，不要报错刷屏。

**4.18.6 失败三态**（v0.12.0）：`call` 返回 `outcome: 'ok' | 'blocked' | 'error'`。`blocked` 是业务拒绝——走到「不通过」节点，或判断不成立且没写「不成立时」要做什么；`error` 是调用或流程本身出错——逻辑不存在、同名歧义、参数不合法、跳转目标丢失、嵌套超过 3 层。`ok` 仍等于 `passed`，只看 `ok` 的旧代码行为不变。`ran` 区分"参数没通过所以没跑"与"跑了但没通过"。

**4.18.7 按 id 调用**：`call` 的第一个参数可以是逻辑 id（`<书id>::L::<序号>`）。先按 id 精确匹配，再按名字；多本书里有同名逻辑且没传 id 时返回 `outcome:'error'` 与 `candidates`，**不再静默取第一个**。

**4.18.8 参数与上下文**：`args` 是对象，键是 `call.params` 里的参数名；返回值带 `unusedArgs`（传了没声明的）与 `missingParams`（声明了没传的），`opts.strict:true` 时直接拒绝。`opts.text/messages/userInput` 可选传入；**默认空上下文**，保住"同楼层重放一致"。

**4.18.9 再抽一次**：同一楼层重复 `call` 默认给同一随机结果；要换结果传 `opts.nonce`（非空字符串），种子由 `api:聊天:楼层:逻辑id:nonce` 组成。

**4.18.10 调用的嵌套**：`call` 内部会注入 `callLogic`，所以逻辑里的「调用逻辑」节点从 UI 调用时也能跑，深度上限 3 层（与聊天内调用同一上限）。

**4.18.11 快照与写入的细节**：`snapshot().books[].logics[].params` 给按钮生成参数输入；`set` 会把 `"5"` 转成 `5`、`"true"` 转成 `true`、空串保持空串，拒绝 `NaN/Infinity` 与非标量；`subscribe` 不防抖、传非函数时只 warn 并返回空退订函数。

**4.18.12 不做 `api.add`**："加一个数"由调用方读 `snapshot().vars`、自己算完再 `set`；同步接口下够用，少一个入口少一套错误语义。

### 4.20 流程的两种写法：表单与文本（v0.13.0 新增；v0.13.1 补直接赋值与 AI 提示词，ILB-4.20.1–4.20.13）

**4.20.1 只有一份流程**：表单视图与文本视图改的是**同一个 `flow.nodes` 节点树**，不存在"文本另存一份"的第二种事实来源。文本层代码在 `core/flow-text.js`，是**纯函数、只做字符串与节点树之间的搬运**，不参与执行——判定仍由 `core/flow.js` 的 `evaluateFlow` 跑节点树。

**4.20.2 不是一门语言**：文本模式是**表单的另一种写法**，不是新语言、没有解释器、没有执行器。谁都不解析"含义"，只做结构翻译；关键词表固定 13 个（检测/判定/比较/定义/计算/随机数/添加/记住/激活/跳转/调用/通过/不通过），值与引用各三种写法，超出这个范围就是"看不懂的行"，报错而不猜。

**4.20.3 值的写法**：`$名字` 变量、`12` 数字、`"文字"` 文本；另放行裸词 `true` / `false`。**4.20.4 引用的写法**：`激活 #条目名`、`调用 >逻辑名`、`跳转 @2✓.1`（位置）。引用一律**按名字**写给人看，找不到时列出候选（"是不是想写：铜钥匙 / 铜门钥匙"）并记为问题行；也接受显式 `#id:xxx` / `>id:xxx` / `@id:xxx`。

**4.20.5 缩进就是分支**：每行一个节点，缩进两格表示"属于上面那个分支"；判定节点的条件写成缩进的 `条件 …` 行；`[存]` 表示计算结果存进聊天，`[小数]`/`[临时]` 修饰随机数。空行与 `//` 注释被忽略。

**4.20.6 往来无损耗，id 除外**：`parseFlowText(renderFlowText(flow))` 结构与原流程一致，唯一例外是节点 id——文本里写的是**位置**（`2✓.1`）不是 id，所以搬回来会给节点换新 id，「跳转」按位置重新指向同一个节点。`tests/flow-text.test.mjs` 用 12 条用例锁住这条契约（含"往返前后 `evaluateFlow` 结果 `deepEqual`"）。

**4.20.7 看不懂的行不生效但不静默**：解析失败的每一行都列成「第 N 行：原因」，能看懂的部分照常生效；界面在流程区域右上角提供「文本模式 / 切回表单」切换，离开文本模式时会把当前文本收成节点树。此约定**不触碰 D-0006**：D-0006 否决的是"支持任意表达式的编辑器"（会退化成代码输入框 + 语法高亮），这里是**固定关键词的另一种写法**，语法能穷举、没有求值能力。

**4.20.8 直接赋值（v0.13.1）**：`计算 $变量 = 值 [存]` 里**没有运算符**时，不是语法错误，而是**直接赋值**——对应 `calc` 节点的 `op: '='`：执行层把右边的值**原样存进变量**（数字、文本、变量都行），不参与算术。表单里的运算符下拉也多了 `=` 这一项，选中后右侧操作数隐藏。成因：AI 写初始化时几乎一律写 `计算 $升级经验 = 0`，而 v0.13.0 只认 `左 运算符 右`，于是整段脚本被判"看不懂"。

**4.20.9 行内注释与行尾说明（v0.13.1）**：`//` 出现在**行尾**时，其后的内容一律当注释丢掉（引号里的 `//` 不算）；「跳转」后面可以跟一句括号说明，如 `跳转 @2 (回到判断所需经验的前一行)`，括号部分被忽略。成因：AI 习惯一行写完再补一句解释。

**4.20.10 报错必须念原文**：解析失败的提示里要带上**这一行原文**，不许拿别处的示例顶替（v0.13.0 曾把「计算要写成：计算 $生命 = $生命 - 1」写死，用户看到与自己的脚本毫无关系的 `$生命`，误以为是 bug）。示例可以是泛化的 `$变量`，但**不能用某个具体业务的名字**。

**4.20.11 警告与错误分开**：`parseFlowText` 返回 `{ flow, problems, warnings }`。`problems` 是"看不懂的行"（该行不生效）；`warnings` 是"看得懂、但大概不是你要的"（目前只有一条：跳转指向自己 → 原地打转，最多跑到 `max` 次），**不影响保存**。界面里 problems 用 `.ilb-bad`（橙红）、warnings 用 `.ilb-warn`（琥珀）。

**4.20.12 给 AI 的提示词（v0.13.1）**：`FLOW_TEXT_AI_PROMPT` + `FLOW_TEXT_AI_TAIL` 是**给模型看的整份格式说明**（关键词表、三种值、位置数法、分支写法、硬规定、一个例子），文本框上方有「复制给 AI 的说明」按钮，点一下进剪贴板（`navigator.clipboard.writeText`，不可用时退回隐藏 textarea + `execCommand('copy')`），用户只需把它粘给 AI 再说自己的诉求，不必自己解释语法。提示词只描述格式、不描述执行——写坏了仍由 `parseFlowText` 一行行报出来。

**4.20.13 手机上至少半屏（v0.13.1）**：`.ilb-flow-area` 在 `max-width: 700px` 下 `min-height: 50dvh`；手机外壳另在 `ui/mobile-skin.js` 里给 `dialog.ilb-m .ilb-flow-area` 同样的下限并放大字号。成因：手机上默认高度只有 180px，手写十几行流程时几乎无法编辑。

## 5 · 注入层

### 5.1 路径优先级（对 v1 的修正）

**ILB-5.1.1** ⛔ v1 的「路径 A：`llm/stream` 请求级改写」**已废弃**。该钩子名在 SillyTavern 公开事件列表中不存在对应项，不应作为主路径。

**ILB-5.1.2** ✅ 注入必须通过可替换的 `InjectionSink` 抽象：

```ts
interface InjectionSink {
  id: "extensionPrompt" | "interceptor" | "promptReady";
  supports: { depth: boolean; role: boolean; textMode: boolean };
  write(blocks: InjectBlock[]): void | Promise<void>;
}
```

**ILB-5.1.3** ✅ 优先级：

1. **`extensionPrompt`（默认主路径）**：`context.setExtensionPrompt()`。SillyTavern 长期提供的正式扩展注入接口，天然满足"不进 chat"，且自带深度与角色参数。
2. **`interceptor`（备用）**：manifest 声明 `generate_interceptor`，拿到构造 prompt 前的消息数组。**必须验证插入后是否泄漏进 chat 正文**（官方文档明确提示消息对象是可变引用，改动会被反映到历史）。若泄漏，必须在下一次读取前回滚。
3. **`promptReady`（最后手段）**：`CHAT_COMPLETION_PROMPT_READY`。该事件在各分支/版本中可写性不一致，**只有在探针验证可写后才允许启用**。

**ILB-5.1.4** ✅ 启动时执行**探针**：注入一段带随机标记的已知文本，检查它是否真的到达出站请求。探针失败 → 降级到下一路径 → 全部失败 → 零注入 + 界面显著提示"当前版本无法注入"。**探针结果必须显示给用户，不能只进 console。**

**ILB-5.1.5** ✅ 探针不得触发真实的模型生成（用 dry run 或在请求构造阶段做判定）。

### 5.2 输出形态

**ILB-5.2.1** ✅ v1 必须同时支持两种 API 形态：

- 聊天补全（`messages[]`）：完整支持
- 文本补全（单一字符串）：通过 `extensionPrompt` 支持位置与深度；`role` 参数无效，诊断中标注"该位置在文本补全下不支持 role"

**ILB-5.2.2** ✅ 注入层必须显式检测当前形态，并在能力不支持某项时**降级而非报错**，同时在诊断里写明降级原因。

### 5.3 位置语义

| ILB position | 含义 | 聊天补全 | 文本补全 |
|---|---|---|---|
| `before_char` | 角色设定之前 | 系统区前部 | 主提示词之前 |
| `after_char` | 角色设定之后 | 系统区后部 | 主提示词之后 |
| `in_chat` + `depth` | 倒数第 depth 条消息之前 | 数组对应位置 | 对应深度 |

**ILB-5.3.1** ✅ `depth` 语义：0 = 最后一条之后，1 = 最后一条之前，依此类推。

**ILB-5.3.2** ✅ 注入层自己计算位置，不依赖原生 world-info 的 `position` 字段或 `@Depth` 宏。

**ILB-5.3.3** ⛔ v1 的「检查目标位置前后是否已有同角色连续消息，必要时合并」**已废弃**：合并会改变正文边界，导致内容粘连。改为：不做任何合并，交给 `setExtensionPrompt` 或宿主自身处理；若目标 API 拒绝连续 system 消息，则由用户在设置中把 `role` 切换为 `user`。

### 5.4 宏替换

**ILB-5.4.1** ✅ 注入前必须在**副本**上对 `content` 执行宏替换（`{{char}}`、`{{user}}`、`{{getvar::x}}` 等，走宿主提供的替换函数）。

**ILB-5.4.2** ✅ 宏替换失败（未知宏、宿主函数不可用）时必须保留原文并记一条诊断，不得抛错、不得清空正文。

**ILB-5.4.3** ✅ 宏替换后的文本才参与预算估算。

### 5.5 与原生世界书并存

**ILB-5.5.1** ✅ ILB 不与原生内容去重、不仲裁、不检测。两者并列注入。

**ILB-5.5.2** ✅ 默认**不加**分隔标记（理由见 ILB-6.5.1）。提供开关，开启时在注入块前加一行轻量标记。标记文本可在设置中改。

**ILB-5.5.3** ✅ 界面上必须有一句固定说明：「ILB 的内容与原生的世界书内容并列加入，不做合并或去重。」

### 5.6 快照校验

**ILB-5.6.1** ✅ `ActivationResult.basedOnMessageCount` 必须在应用前与当前消息数比对；不一致则丢弃本轮结果并记诊断。

**ILB-5.6.2** ✅ 判定与注入之间不得 `await` 任何网络请求。

## 6 · 界面与文案

### 6.1 面板（v0.8.2 起为六个）

> 🔁 修订（v0.8.2）：面板从五个变成**六个**，新增「状态」（变量与条目字段）。见 ILB-6.1.5；原五条不变。

**ILB-6.1.1** ✅ 界面只有五个主要面板，不得无限扩张：

1. **书架**：有哪几本书、**每本的启用方式（永远 / 跟随角色卡 / 手动）与手动开关**、**是否参与全局池**、哪本在本轮生效及原因、每本占多少 token、来源文件与导入次数
2. **规则**：一本书的规则列表与编辑器（原"条目"与"规则表"合并为一页：列表本身就能一眼看懂"什么条件 → 出哪条"，点开才进编辑器）

5. **设置**：全局默认值、导入策略、总开关

**ILB-6.1.3** ✅ 面板与外壳必须能独立替换：删掉浮窗外壳时，面板仍可被挂到任意容器里显示；反之换一套外壳（例如将来做成侧边栏）不需要改面板。

**ILB-6.1.4** ✅ 面板本身只是**路由**：每个标签页的渲染函数单独成文件（`ui/view-*.js`），任一页抛错只坏那一页，其余页仍然可用（ILB-2.5）。

**ILB-6.1.5** ✅ 第六个面板是「状态」（v0.8.2 新增）：这一场聊天的变量表 + 条目声明的字段控件。它只读写聊天变量，不碰书和规则；换聊天换一套（ILB-10.18）。

### 6.2 规则表视图（低门槛的落点）

**ILB-6.2.1** ✅ 条目列表必须提供一个"规则表"视图，一行一条规则：

```
触发词                         →  出哪条            状态
──────────────────────────────────────────────────────
说到「王城」                    →  王城·通用          ✅ 本轮出现
说到「王城」+「夜晚」           →  王城·夜巡          ✅ 本轮出现
说到「王城」+「夜晚」+「叛乱」   →  王城·叛乱          ⬜ 差一个词
```

**ILB-6.2.2** ✅ 规则表必须支持就地编辑：点词改词、点条目换条目、拖动改优先级。**不允许为了改一个词跳转到另一个页面。**

**ILB-6.2.3** ✅ 所有复杂条件（`when` 卡片）的入口是规则表行尾的「＋条件」。点开后是卡片选择器（三种卡片 + 并且/或者），**不出现任何输入框要求用户写字法**。

**ILB-6.2.4** ✅ 组合特化（A / A+B / A+B+C）不引入新语法，用「同组 + 权重 + 拖拽顺序」表达。界面必须显示为同一组下的条目，且允许拖动排出"越靠上越具体"。

**ILB-6.2.5** ✅ 任一控件必须在 hover 时显示它影响的具体后果，例如预算滑块旁显示"当前这本书会占用约 1,200 tokens"。

### 6.3 诊断面板

**ILB-6.3.1** ✅ 每次生成后，诊断面板必须能回答三个问题：注入了哪几条、跳过了哪几条、每一条跳过的是哪个环节（触发词 / 条件 / 时效 / 概率 / 同组 / 预算 / 连锁）。

**ILB-6.3.2** ✅ 每条跳过原因必须是完整人话，例如「《王城·夜巡》这轮没出现：触发词「夜晚」在最近 3 条消息里没找到」，而不是 `no match`。

**ILB-6.3.3** ✅ 诊断面板默认折叠，但「本轮注入了 N 条 · 跳过 M 条」这一行必须默认可见。

### 6.4 帮助按钮（每页一个，醒目）

**ILB-6.4.1** ✅ 每一个面板、每一个复杂控件区，都必须有一个**醒目的**帮助入口（圆形 `？` 按钮，位于该区域标题右侧，颜色与主操作区分）。

**ILB-6.4.2** ✅ 点击后在原地弹出浮层，不跳页、不打开新窗口。浮层内容固定三段：

1. **这是什么**：一句话，不用术语
2. **它会影响你的对话什么**：一句，讲清代价或收益（例如"开得越多，每轮花的 token 越多"）
3. **一个例子**：可直接照抄的具体例子

**ILB-6.4.3** ✅ 帮助文案存放在 `data/help/<locale>.json`，key 与界面元素 ID 一一对应。**新增界面元素而不补帮助文案，视为未完成。** 这条在验收清单（ILB-9.3）中单独检查。

**ILB-6.4.4** ✅ 帮助文案必须能脱离代码更新（改 JSON 即生效，刷新页面即可）。

**ILB-6.4.5** ✅ 默认值必须在对应帮助浮层里写明"为什么默认是这个值"，并给出一句"什么时候你该改它"。

**ILB-6.4.6** ✅ 帮助浮层底部固定一行：「默认值是给大多数人的起点，不是推荐值。」

### 6.5 默认值

**ILB-6.5.1** ✅ 默认值如下。每一项都必须能一句话说清"为什么是这个"：

| 项 | 默认 | 理由 |
|---|---|---|
| 总开关 `enabled` | 开 | 出问题时要能一键停掉；但默认必须开着，否则装了等于没装（ILB-6.9.3） |
| 扫描深度 `scanDepth` | 3 | 再深就开始把早期剧情当触发源，误触发比漏触发更烦人 |
| 预算 | `min(上下文×15%, 2000)` | 给主剧情留足空间，同时能装下一本中等体量的书 |
| 概率 | 关闭（视为 100） | 默认结果必须可复现，开启随机是高级玩法 |
| 连锁 | 开启，深度 3 | 涌现是核心卖点，但 3 层足够且可控 |
| 导入条目参与连锁 | 否 | 第三方书互引多，默认关掉避免预算被撑爆 |
| 同组择一 | 权重最高者 | 越具体越优先，符合直觉 |
| 排序 | 权重 → 用户拖拽位次 → id | 稳定排序，保护提示词缓存 |
| 注入位置 | `after_char` | 与多数预设的既有习惯一致 |
| `in_chat` 默认深度 | 4 | 适中距离，不打断最近的对话 |
| 时效 | 全关（0） | 需要的人会开，不需要的人会被它坑 |
| 跟随角色卡自动选书 | 开 | 这是低门槛的核心，不做就等于每张卡都要手动配 |
| 分隔标记 | 关 | 标记每轮都要花 token，收益不确定 |
| 注入角色 | `system` | 与预设习惯一致；文本补全下自动忽略 |
| 帮助按钮 | 全开 | 没有理由关 |

**ILB-6.5.2** ✅ 默认值的选择原则：**宁可保守，也不要激进。** 默认不启用可能让人困惑的功能，用帮助浮层告诉用户"它存在，什么时候可以打开"。

**ILB-6.5.3** ✅ 默认值可能不合多数人口味——这是已知且已接受的事实。补偿手段是：帮助浮层（ILB-6.4）、诊断面板（ILB-6.3）、一键恢复默认、以及每个设置项的"改这个会发生什么"提示。**不用市场调研来定默认值，用可解释性来弥补。**

### 6.6 空状态与首次引导

**ILB-6.6.1** ✅ 第一次打开且没有任何书时，界面必须显示三步引导：导入一本书 → 看规则表 → 发一条消息看诊断。三步都做成可点击的入口，不要求用户先读任何文档。

**ILB-6.6.2** ✅ 空状态不得出现空白页或纯技术提示（如"no books found"）。

### 6.7 AI 体检（可选功能）

**ILB-6.7.1** ✅ 提供「体检」按钮：扫描常驻条目，识别出"正文里写了条件、但结构上是常驻"的条目，给出**建议卡片**供用户逐条接受/忽略。

**ILB-6.7.2** ✅ 体检**只允许在用户点击时运行**，绝不在生成路径上运行。

**ILB-6.7.3** ✅ 体检可以调用宿主的模型接口（`generateQuietPrompt` + 结构化输出）生成建议，但：

**ILB-6.8.9** ✅ 手机上不得出现"必须横向拖动才能用"的表格作为主要操作方式。宽表允许横向滚动，但**主操作按钮必须在首屏可见**。

### 6.9 界面状态不参与判定

**ILB-6.9.1** ✅ 窗口位置、尺寸、悬浮球位置、上次是否打开，存放在 `extension_settings.independent_lorebook.ui`，**只经 `repository.getUiState/saveUiState` 读写**。它们不得进入 `EvalRequest`，也不得出现在 `ActivationResult`。

**ILB-6.9.2** ✅ 删掉整个 `ui` 桶，判定结果必须完全不变。这是判断"界面状态有没有渗进逻辑"的可执行检查。

**ILB-6.9.3** ✅ 唯一允许改变"这一轮有没有注入"的界面状态是总开关 `settings.enabled`。它必须在判定开始前统一处理：关闭时清掉上一轮注入残留、不判定、不报错，原因记为"故意没做"而非"出错"。

### 6.10 搜索与筛选（v0.3.0 新增）

**ILB-6.10.1** ✅ 任何**出现选择**的界面（书架、规则列表、导入选择、规则里选"哪条已出现"）都必须带搜索与筛选。书一多，靠翻页找目标是最先崩掉的体验。

**ILB-6.10.2** ✅ 搜索范围必须同时覆盖：条目标题、正文、分组、触发词（含正则源码）。理由：用户常常只记得"里面写过某个词"，未必记得标题。

**ILB-6.10.3** ✅ 多个关键词用空格分隔，语义是**并且**（全部命中）。这样"王城 夜巡"能缩小范围，而不是越搜越多。全角空格与逗号同样视为分隔符。

**ILB-6.10.4** ✅ 可筛选的维度：分组、规则状态（全部 / 已启用 / 已停用 / 常驻 / 靠触发词 / 允许连锁）、书的启用方式与是否入池。

**ILB-6.10.5** ✅ 必须显示"命中 N / 共 M"，让用户知道自己有没有被筛掉。只说"共 M 条"会让人以为筛选没生效。

**ILB-6.10.6** ✅ 规则列表中的每条规则必须有"试一句"入口（ILB-4.9）。搜索 + 试一句组合起来，才回答得了"我写的判定到底管不管用"。

**ILB-6.10.7** ✅ **规则列表在手机上不得需要左右滑动。** 一条规则是一张卡片：允许上下变长，不允许横向撑出屏幕。所有横向排列的容器都要能换行（`flex-wrap`），宽度用 `flex-basis + min-width: 0`，先缩再换行；禁止用固定 `min-width`（如 520px）把表格撑出可视区。这一条是硬性验收项。

### 6.11 快照（v0.3.0 新增）

**ILB-6.11.1** ✅ 快照记录的是**"这一轮想用哪些条目"**，不是"这些条目写了什么"。每本书存：`book_id`、书名、启用方式、是否入池、手动开关、每个条目的 `id / title / enabled / always`。**不存正文、不存触发词、不存注入位置**。理由见 D-0021：切风格不该改正文，否则用户切两次快照就可能把写好的内容弄丢。

**ILB-6.11.2** ✅ 两类快照，上限分开算：**常用**（有名字）10 份、**临时**（没名字）5 份。

**ILB-6.11.3** ✅ 超出上限时按"最近使用"淘汰最旧的一份。改名把临时快照提升为常用时，记 `promotedAt` 作为排序依据——否则它一升级就会因为 `at` 太旧而被立刻顶掉。

**ILB-6.11.4** ✅ 恢复快照前必须**自动备份当前状态**为一份临时快照（标注"恢复前自动备份"）。切错了还能退回来。

**ILB-6.11.5** ✅ 恢复后必须报告：动了几本书、几条开关变了、哪些书已不存在、多少条后来删掉的没恢复。快照里没有的条目保持原样，不得被清空。

**ILB-6.11.6** ✅ 快照不进入 `EvalRequest`，不参与判定；它只在"应用"那一刻改书与手动开关。

### 6.12 批量操作（v0.3.0 新增）

**ILB-6.12.1** ✅ 批量必须建立在**当前筛选结果**上：先搜/筛，再"全选当前结果"，再执行。理由见 D-0022：批量最危险的是"看不见的东西也被改了"。

**ILB-6.12.2** ✅ 换一次筛选，之前勾选但已不可见的条目自动作废。这一条必须在代码里强制，不能靠提醒用户。

**ILB-6.12.3** ✅ 可批量执行的只有：启用、停用、设为常驻、取消常驻、删除。**不允许**批量改正文、触发词、注入位置——那些是"逐条判断"的事，批量一定会出事。

**ILB-6.12.4** ✅ 批量删除必须二次确认；其余批量操作只需一条 toast 说明改了几条。

### 6.13 流程编辑器（v0.4.0 新增）

**ILB-6.13.1** ✅ 编辑器是**树形块**，不是连线画布：每个节点一张卡，判断节点下面直接长出「✓ 成立时」与「✗ 不成立时」两块，块里可以继续放节点。理由见 D-0026：手机上拖线、找端口、缩放画布都点不准；而用户心里想的本来就是"下一步做什么"，不是"把线连到哪个口"。

**ILB-6.13.2** ✅ 每条规则的流程**默认是空的**，界面上第一句必须写清楚："不画任何一步，这条规则就完全按上面的触发词和下面的注入参数工作——和原生世界书一样。"

**ILB-6.13.3** ✅ 每个节点卡片的标题行必须同时给出：节点种类的中文名、这个节点在做什么的一句话（`describeNode`）。不允许只显示 `test` / `compare` 这种内部名字。

**ILB-6.13.4** ✅ 增删节点、上下移动、切换分支都只改模型；结构性变更才整体重绘，输入框用 `oninput` 直接写模型——否则每敲一个字就丢焦点。

**ILB-6.13.5** ✅ 规则列表的卡片上要有一个徽标：没有流程不显示；有流程显示「有流程」；`mode: "only"` 显示「只看流程」，让用户一眼看出"这条的判定不普通"。

**ILB-6.13.6** ✅ 编辑器里点「编辑流程」是**原地展开**，不弹新浮层。理由：帮助浮层是单层的，弹第二层会把第一层（正在编辑的规则）顶掉，用户填了一半的内容会没。

**ILB-6.13.7** ✅ 手机上不允许横向滚动：所有表达式行、条件行一律 `flex-wrap`，窄屏时输入框各占一行。

**ILB-6.13.8** ✅ 每条流程字段都要能一句话解释；「不成立时」留空的后果（这条规则不出现）必须印在那一块里，不能只写在文档里。

### 6.14 浮层与次级菜单（v0.4.2 新增）

> 来源：真机测试发现"手机上点「试一句」「导入原生世界书」「导入记录」，弹层位置过于靠上，右上角关闭按钮点不到"。
> 这不是某一个弹层写错了，而是**定位策略**错了：`align-items: center` + 内容比屏幕高时，溢出的部分会被平均顶到屏幕上方，标题和关闭按钮正好一起被顶出可视区。所以约束写在"所有浮层的共同出口"上。

**ILB-6.14.1** ✅ 所有次级菜单（帮助、试一句、规则编辑、导入选择、导入结果、导入记录、检查原件、检查结果、恢复默认值）必须走同一个出口 `ui/help.js` 的 `openOverlay()`，**不允许各界面自己拼一层 `.ilb-overlay`**。理由：这类"某一处点不到的弹层"只会有一个成因，但补丁会散落在十处。

**ILB-6.14.2** ✅ 浮层容器用**顶对齐 + 自身可滚动**（`align-items: flex-start; overflow-y: auto`），弹层用 `margin: auto` 居中。禁止只写 `align-items: center` 而不处理溢出——那正是"按钮被顶出屏幕"的写法。

**ILB-6.14.3** ✅ 关闭按钮用「×」，`aria-label="关闭"`，可点区域不小于 44×44（手机）；标题过长时省略，不允许把关闭按钮挤到换行或屏幕外。

**ILB-6.14.4** ✅ 标题栏是**固定块**、正文单独滚动（`.ilb-modal-body { overflow-y: auto }`）。用户滚正文时，关闭按钮必须一直在。

**ILB-6.14.5** ✅ 手机（宽度 ≤768px）上，浮层是**从底部升起的整宽面板**：`align-items: flex-end`、`width: 100%`、`max-height: calc(100dvh - 12px)`，并留 `env(safe-area-inset-bottom)`。理由：屏幕越大，居中弹窗的关闭按钮越往屏幕上半部跑；贴底则永远在拇指附近。
> ⛔ 已废弃（0.5.0）。原文：手机浮层由 `.ilb-overlay` / `.ilb-modal` 加媒体查询贴底整宽。替代：ILB-6.19.7——手机上的次级菜单改成整屏 `<dialog>` 里的**二级页**（从顶部占满、标题栏固定、正文单独滚动），贴底那套 CSS 已从 `style.css` 删除。

**ILB-6.14.6** ✅ 浮层打开时锁住背景滚动（`body.ilb-locked`，只在窄屏生效，避免桌面端出现布局跳动），关闭时立即解除；锁与解锁必须成对，不能靠"用户点了遮罩"来保证。
> ⛔ 部分废弃（0.5.0）：`ilb-locked` 类不再使用；手机锁滚动由 `ui/mobile.js` 直接写 `body.style.overflow`（替代：ILB-6.19.5），电脑那套仍不锁（避免布局跳动）。"锁与解锁必须成对"继续有效。

**ILB-6.14.7** ✅ 浮层必须挂在 `document.body` 上，不能挂在浮窗（`.ilb-window`）内部：浮窗有 `overflow: hidden` 与变换，`position: fixed` 在里面会被裁掉或被当成相对浮窗定位。

**ILB-6.14.8** ✅ 验收：375px 宽度下逐个打开上面列出的全部次级菜单，关闭按钮必须在首屏可见且点击有效；这条写进 §9.3。

### 6.15 失败必须出声（v0.4.3 新增）

> 来源：用户报告"点击按钮没有界面弹出，只有导出能用"。这类故障最要命的不是坏，而是**坏得安静**：用户看到的是"点了没反应"，控制台可能一片空白，开发者拿不到任何线索。
> 处置原则：先量事实，再改代码。此处新增的都是"让事实可见"的设施，不是猜出来的修法。

**ILB-6.15.1** ✅ 每一次打开浮层都要在控制台留一行 `[ILB] 浮层已打开：<标题>`。它回答的是"点击处理器到底有没有走到这一行"，这是排查"没反应"的第一个分叉点。

**ILB-6.15.2** ✅ 浮层挂上之后必须**量一次**（`getBoundingClientRect` + `getComputedStyle`）：若 `display:none`、`visibility:hidden`、`position` 不是 `fixed`，或尺寸小于 8px，视为样式没生效，立刻用内联样式兜底并 `console.warn`。理由：缓存了旧 CSS、主题覆盖、别的扩展改了选择器，都会表现为"点开但看不见"，而控制台不说话。

**ILB-6.15.3** ✅ 未捕获的错误与未处理的 Promise 拒绝必须转成界面上的一句话（toast），并保留完整原始错误在控制台。禁止让点击处理器里的异常静默消失。

**ILB-6.15.4** ✅ 需要等待宿主数据的界面（导入列表、检查原件）必须**先把浮层开出来**再等待，并在浮层里写明"正在读取…"；失败时把原因写在浮层里，而不是只弹一个可能被忽略的 toast。

**ILB-6.15.5** ✅ 必须提供**一键自检**（设置页「运行自检」）。它只读、不改数据，检查：样式表是否加载并解析、浮层规则是否生效、浮层能否真的开出来并铺满视口、关闭按钮是否存在、扩展与管线是否就绪。结果必须可整段复制。

**ILB-6.15.6** ✅ 布局类结论必须用**真实浏览器**量，不能用假 DOM 推断。仓库内提供 `tests/browser-probe.html`：无头 Chrome 打开它，即可读到浮层矩形、关闭按钮尺寸、是否铺满视口，以及自检的逐条结果。

**ILB-6.15.7** ✅ 验收：在干净页面里，手机与桌面两种视口下浮层都铺满视口、关闭按钮在视口内；自检除"未加载宿主"外不得有失败项。这条写进 §9.3。

### 6.16 浮层必须真的在最上层（v0.4.4 新增）

> 来源：用户报"手机上点按钮没有界面弹出，PC 上正常"。查下来不是没弹，而是**弹出来的浮层被 ILB 自己的浮窗盖住了**——手机上浮窗是整屏的（`z-index: 4500`），浮层一旦被压到它下面，整块就消失；桌面上浮窗只占一角，所以看着像"正常"。
> 这是最阴的一类：**打开浮层的代码跑了、日志也打了、尺寸也对**，只有"谁在上面"是错的。所以约束必须写成"可以验证的"。

**ILB-6.16.1** ✅ 浮层的层级必须远高于自家其他界面（`.ilb-overlay` 用 `z-index: 2147483000`），不允许只比浮窗高一点（如 4600 对 4500）。理由：只要有一条别的规则把浮层压回去（旧缓存、主题覆盖、别的扩展改选择器），差值 100 立刻失效；而"接近上限"在任何组合下都压不过。

**ILB-6.16.2** ✅ 浮层开着时，自家浮窗、悬浮球、遮罩必须让开（`body.ilb-overlay-open` → `visibility: hidden`），关闭时成对恢复。**不靠 z-index 排序来保证"看得见"**：排序是推断，隐藏是事实。
> 🔁 修正（0.5.0）：遮罩 `.ilb-backdrop` 已随手机变体删除，现在让开的是浮窗与悬浮球两项（手机侧则是 top layer，天然压住一切，见 ILB-6.19.2）。

**ILB-6.16.3** ✅ 打开浮层后必须用 `document.elementFromPoint(屏幕正中)` 实测一次"最上面是谁"；若命中的不是浮层内部，判定为被遮挡，立即把浮层内联提到最上层并 `console.warn` 说明被谁挡住（元素名、class、z-index）。

**ILB-6.16.4** ✅ 自检（§6.15.5）必须包含两条：浮层层级是否高于浮窗；屏幕正中那一点的最上层元素是否属于浮层。这两条要能单独看出，不许合并成一句"界面正常"。

**ILB-6.16.5** ✅ 验收：手机上把浮窗开着（整屏），再打开任意次级菜单，内容必须可见、可点；`tests/browser-probe.html` 里的"模拟整屏浮窗"场景必须 PASS。这条写进 §9.3。

### 6.17 浮层不能变成"很薄的一排"（v0.4.6 新增）

> 来源：用户报"点击按钮之后，页面会正常弹出，可是只有高度非常小的一排，大概只覆盖了原本顶部的几个选项按钮"；并且明确"PC 端没有任何问题，只有手机端"。
> 两个原因叠在一起才出现：
> 1. **手机那套样式根本没生效**。SillyDroid 这类手机客户端的 WebView 常按"桌面宽度"排版（例如 980px），于是 `@media (max-width: 768px)` 不成立，手机拿到的是电脑规则——弹窗从顶上开始排、按桌面宽度算，而不是贴底整宽。
> 2. **内容还没到**。导入浮层要等原生世界书列表读回来；渲染若失败，正文可能是空的。桌面规则下"高度由内容决定"，空内容 + 顶对齐 = 一条细缝。

**ILB-6.17.1** ✅ 布局判定必须有两把钥匙：CSS 媒体查询（`max-width: 768px`）+ JS 判定后写在 `body` 上的 `ilb-mobile` 类。两者按同一套规则写样式，任一成立就生效。**不许只留媒体查询**：手机上"屏幕窄"与"CSS 宽度窄"是两件事，WebView 会骗人。
> ⛔ 已废弃（0.5.0）。原文：同一套浮层用媒体查询与 `body.ilb-mobile` 两把钥匙切成手机形状。替代：ILB-6.19.3——手机改成自带皮肤的独立外壳，既不需要媒体查询、也不需要 `body` 上的类；两把钥匙与 `.ilb-mobile` 规则已从 `style.css`、`ui/help.js` 删除。这一条废弃的是**做法**，"WebView 的 CSS 宽度会骗人"这个判断仍然成立，正因如此才不再依赖任何媒体查询。

**ILB-6.17.2** ✅ 浮层盒子必须有高度下限（`.ilb-modal { min-height: 160px }`）。理由：内容为空、加载中、渲染失败时，视觉上仍要能认出"这是一层浮层"，而不是页面抖了一下。

**ILB-6.17.3** ✅ 打开后必须量一次真实高度：若弹窗高度 `< min(180px, 视口高 × 0.2)`，判定为"太扁"，立即内联 `min-height: 45vh` 并 `console.warn` 说明量到的数值与视口尺寸。**这是自愈，不是修正样式**：样式该修的要修，但不能指望用户永远能抢先加载到新 CSS。

**ILB-6.17.4** ✅ 若浮层正文没有任何子节点，必须插入一句人能读懂的原因（"这一层浮层没有内容（可能是渲染时出错了）……"）。**不许留一层空白浮层**：空白等于让用户以为按钮坏了。

**ILB-6.17.5** ✅ 自愈检查不能只依赖 `requestAnimationFrame`：后台标签页、部分 WebView、无头浏览器都会把它节流甚至不触发。必须同时安排一次定时兜底（400ms），并用"只跑一次"的标记保证两路不重复执行。

**ILB-6.17.6** ✅ 验收：`tests/sizing-probe.html` 在 `390×844` 与 `1280×800` 两个窗口下，四种情况（短内容、长内容+底栏、空内容、强制手机布局）必须全部 PASS；空内容那组的弹窗高度必须明显大于一行标题栏。这条写进 §9.3。
> ⛔ 已废弃（0.5.0）。原文：用 `tests/sizing-probe.html` 验收"手机变体不变成一条缝"。该探针已随手机变体一起删除。替代：ILB-6.19.10 的 `tests/mobile-ui-probe.html`（375×780 带样式与不带样式各一轮 + 500×900 + 820×620 电脑布局）。

**ILB-6.17.7** ✅（v0.4.7 新增）四条"绝不能失效"的几何必须在打开时就内联写上，不许只靠样式表：`position: fixed`、`inset: 0`、`display: flex`、`z-index`（浮层），以及弹窗的 `min-height`（手机 `45vh`、电脑 `160px`）。理由：这四条一旦失效，用户看到的就是"点了没反应"或"一条缝"，而它们恰恰最容易被旧缓存、主题、别的扩展改掉；内联样式谁也抢不走，其余观感仍交给 CSS。
> ⛔ 部分废弃（0.5.0）：手机那个 `45vh` 分支随手机变体作废（替代：ILB-6.19.2，手机外壳的尺寸由 `visualViewport` 直接写内联，含 `min-height` 语义）。电脑的四条几何继续有效，`min-height` 固定 `160px`。
> 反面证据（用户回报的 DOM）：浮层与弹窗上带着整串 `style="position: fixed; inset: 0px; …"`，说明当时走的是"样式没生效 → 内联兜底"这条路；而兜底当时**没有写 `min-height`**，于是兜底本身又把用户送回了"很薄一排"。兜底不是把样式重写一遍就完事，兜底必须比样式表更保守地保证"看得见"。

**ILB-6.17.8** ✅（v0.4.7 新增）自检必须报"数"而不是报"感觉"：①`style.css` 里数到多少条 `.ilb-` 规则（少于 20 条即判定为旧版本或被截断）；②真实打开一层浮层后量弹窗高度、计算出的 `min-height`、以及当前是手机还是电脑布局；③弹窗上有没有就地固定的最小高度。用户回报问题时只需要贴自检结果，不必理解 CSS。

### 6.18 看不见的浮层（v0.4.8 新增）

> 这一节来自一次很典型的误判：v0.4.7 把四条几何内联钉死之后，用户说"不是一小条了，但是点击按钮后，没有页面弹出，或者单纯没有显示"。
> 真实原因是：几何是内联的、尺寸与位置全对，但**底色、边框、文字颜色仍然来自那份没生效的样式表**。
> 于是屏幕上有的只是一层透明的全屏容器里套一个透明的盒子——"在，但看不见"。
> 教训：**"渲染出来了"和"看得见"是两件事。** 只量尺寸会漏掉整整一类故障。

**ILB-6.18.1** ✅ 可见性检查必须同时看三件事，缺一即判定为"样式没生效"：①位置与尺寸（`position` / 是否铺满 / 弹窗宽高）；②**底色**（浮层与弹窗的背景都必须不透明）；③正文是否有内容。三件事都通过，才允许 `console.debug` 说"检查通过"。

**ILB-6.18.2** ✅ 透明度判定不许用字符串相等（`'transparent'` 与 `'rgba(0, 0, 0, 0)'` 在不同浏览器里写法不同）。必须解析 `rgb()` / `rgba()`：三个分量视为不透明，四个分量则要求 alpha > 0.01。

**ILB-6.18.3** ✅ 兜底必须是"**皮肤**"，不能只是"位置"。兜底时至少要给：浮层半透明黑底与层级；弹窗背景色、文字色、边框、圆角、阴影、`display: flex` 纵排；标题栏的左右分布与下边框；正文区的内边距与滚动；关闭按钮的最小可点面积。**理由**：只补位置等于把"一条缝"换成"一块隐形玻璃"，用户仍然会认为按钮坏了。

**ILB-6.18.4** ✅ 自检必须报出两个底色（浮层与弹窗），并明确写"透明，等于没显示"。用户只需贴这一行，就能区分"没渲染"与"渲染了但看不见"。

**ILB-6.18.5** ✅ 验收：`tests/nocss-probe.html`（**故意不加载** `style.css`）在 `390×844` 下必须八条全过：浮层铺满、浮层有底色、弹窗有底色、弹窗高 ≥120、弹窗宽 ≥ `min(280, 视口-40)`、正文文字还在、关闭按钮在、控制台说明了兜底原因。另有手工验收：用开发者工具删掉 `style.css` 的 `<link>` 后再点任意按钮，浮层与弹窗仍然可见。
> 🔁 补充（0.5.0）：这一条现在只覆盖**电脑**。手机的对应验收是 `tests/mobile-ui-probe.html` 里"不加载 style.css"那一轮（ILB-6.19.10）——手机皮肤是自带的，不靠兜底。

**ILB-6.18.6** ✅ 兜底触发时必须有且只有一句 `console.warn`，写明命中了哪一项（`弹窗背景是透明的（rgba(0, 0, 0, 0)）` 这类）。**不许静默**：静默兜底会让"样式表没加载"这种根因永远查不出来（ILB-6.15.1 的延伸）。

### 6.19 手机界面独立成套（v0.5.0 新增）

> 来源：用户（m00002）报"竖屏或手机比例之下，点了按钮之后 UI 不显示"，并明确 v0.4.2–v0.4.8 四轮修补都没解决；用户提出不要再让手机与电脑共用一套 UI 的变体，而是**彻底为手机重写一套**，只保留旧 UI 在电脑上生效。
> 依据：在合成环境里（真实 `style.css` + 真实模块 + 500×749 手机布局）浮窗与浮层全部正常，故障无法复现——说明根因不在几何计算，而在"同一套 DOM 被改形"这条路上（D-0037）。所以停止在该方向继续加兜底，改为换壳。
> 这也是一条**方法论修正**：连续四轮"再补一条兜底"没有一次被真机确认，等于用抽奖换 token。换壳的代价是一次性重写，收益是手机不再继承任何一版历史兜底。

**ILB-6.19.1** ✅ 手机与电脑是**两套独立外壳、共用一个面板**：电脑走 `ui/floating.js`（悬浮球 + 可拖动浮窗 + `ui/help.js` 的浮层），手机走 `ui/mobile.js`（悬浮球 + 整屏 `<dialog>` + 二级页栈）。挑哪套、何时切换只在 `ui/shell.js`；`ui/panel.js` 与五个视图不认识外壳（ILB-6.1.3 的落地）。

**ILB-6.19.2** ✅ 手机外壳必须用原生 `<dialog>` + `showModal()`：它进浏览器的 **top layer**，不受任何祖先的 `overflow`/`transform`/`z-index`/`filter` 影响。`showModal` 不可用（老 WebView）时退回"内联固定层"，并在控制台说明走了哪条路。

**ILB-6.19.3** ✅ 手机外壳的样式必须自带（`ui/mobile-skin.js` 注入 `<style id="ilb-mobile-skin">`），**不依赖 `style.css` 是否加载**；选择器统一 `.ilb-m` 前缀，避免与电脑那套互相污染。自检必须报出皮肤是否注入、规则条数、版本。

**ILB-6.19.4** ✅ 开关只认 `click`。手机外壳的悬浮球与按钮不得靠 `pointerdown`/`pointerup` 配对来判定"点了一下"：WebView 的手势识别会取消 pointer 事件，`pointerup` 可能永不到达，表现就是"点了没反应"（D-0038）。

**ILB-6.19.5** ✅ 手机外壳的尺寸由 `window.visualViewport` 算（`height`/`offsetTop`/`width`），不让 `100vh`/`100dvh` 单独承担；地址栏伸缩、软键盘弹出后必须仍然铺满可视区。整屏界面打开时由外壳直接锁 `body` 滚动，关闭即解锁（成对）。

**ILB-6.19.6** ✅ 手机上的提示不能用宿主 toastr：`showModal()` 把界面放进 top layer，宿主的 toastr 在其下方，用户看不见。外壳提供自己的 `toast()`——界面开着时画在界面里（最多 3 条、自动消失），关着时退回宿主出口。

**ILB-6.19.7** ✅ 手机上所有次级菜单（帮助、试一句、规则编辑、导入选择/结果/记录、检查原件/结果、恢复默认值）仍走同一出口：`ui/help.js` 的 `openOverlay()` 经 `setOverlayBackend()` 转给手机外壳，压进**二级页栈**。返回键/`cancel` 先关栈顶，栈空才关整屏；每层标题栏有「×」与「←」，热区 ≥44×44；空正文必须写人话。

**ILB-6.19.8** ✅ 375px 宽下不得横向滚动：一律 `min-width: 0`、`flex-wrap`、`overflow-wrap: anywhere`；输入框 `font-size: 16px`（防 iOS 聚焦自动放大）。验收必须用真实窄视口（探针里的 375px iframe 或真机），**不得用桌面缩窗代替**。

**ILB-6.19.9** ✅ 手机界面打开后必须自量一次（`requestAnimationFrame` 两次 + 400ms 定时兜底，只跑一次）：`display`/`visibility`/尺寸/底色，以及 `elementFromPoint(屏幕正中)` 是否落在界面内；任一不对就地内联兜底并 `console.warn` 写明命中项。

**ILB-6.19.10** ✅ 验收：`tests/mobile-ui-probe.html` 四轮全 PASS——375×780 带样式、375×780 **故意不加载 `style.css`**、500×900、820×620（期望电脑布局，确认手机界面不越权接管）；`tests/shell-route-probe.html` 三轮全 PASS——同一套装配在 375 与 900 视口下分别挑中手机/电脑壳，另一套整体让位，`shell.notify` 落在当前看得见的那套里；自检在手机与电脑两种布局下都不得有非预期失败。这条写进 §9.3。

**ILB-6.19.11** ✅ 电脑那套的 `ui/help.js` 只服务电脑：不得再读"是不是手机"来决定样式，也不得给 `body` 打 `ilb-mobile` 类。手机相关的类名、媒体查询、内联兜底从 `style.css` 与 `ui/floating.js` 中删除，不保留"以防万一"的副本。

## 7 · 已知坑与对策

> 每一条都是"按本规格实现时一定会遇到"的问题，不是提醒。编号可单独引用。

**ILB-7.1 注入路径的可写性不确定。**
不同 ST 版本/分支对 `CHAT_COMPLETION_PROMPT_READY` 的处理不同：有的当通知事件，有的可写。只依赖它会出现"日志说注入了，模型没收到"的静默失败。→ 对策：ILB-5.1.4 探针 + 结果可见。

**ILB-7.2 `chat` 数组是活引用。**
判定期间用户切换聊天、发新消息、roll 分支，快照会与注入时的实际内容不一致。→ 对策：ILB-4.1.3 快照 + ILB-5.6.1 长度校验。

**ILB-7.3 与原生并存会重复。**
两套内容都进 system 区，可能互相矛盾。ILB 不负责仲裁。→ 对策：ILB-5.5.3 固定说明，不试图智能去重（那会重新引入对原生管线的依赖）。

**ILB-7.4 精确 token 数拿不到，且不能等。**
`getTokenCountAsync` 是异步的，注入路径不能 await 它。→ 对策：ILB-4.7.3 字符估算 + 异步回填。

**ILB-7.5 `constant: true` 的条目可能残留非空 `key`。**
用"key 是否为空"判断是否常驻会漏掉这类脏数据。→ 对策：以布尔 `constant` 为准，`key` 非空时发警告（ILB-3.3.7）。

**ILB-7.6 正则 ReDoS。**
第三方书的 pattern 可能在生成关键路径上造成指数级回溯、卡死界面。→ 对策：单条正则执行设时间预算（10ms），超时视为未命中并记诊断；导入时对嵌套量词给出警告。

**ILB-7.7 多书同时启用时条目 ID 冲突。**
同一源书派生的两本书会有重复 id。→ 对策：加载时强制 `<book_id>::<id>` 前缀（ILB-3.4.1）。

**ILB-7.8 设置写入竞争。**
多个扩展同改 `extension_settings` 时，谁先保存谁赢，后保存的会覆盖别人的字段——如果它整份替换的话。→ 对策：ILB-3.1.2 只改自己的命名空间 `extension_settings.independent_lorebook`，从不整份替换 `extension_settings`；每次写完立刻交给宿主的去抖保存（`saveSettingsDebounced`），避免"改了没落盘"（v2.1.1 修正：此前写的"独立文件为主存储"与 ILB-3.1.2 冲突，前端扩展没有写文件的权限）。

**ILB-7.9 连锁爆炸。**
第三方书互引密集时，3 层连锁可能把预算瞬间吃满。→ 对策：连锁条目计入同一预算；`chain.participate` 默认关（ILB-4.6.4）；诊断显示连锁来源。

**ILB-7.10 宏替换时机。**
导入时替换会把 `{{user}}` 固化成当时的用户名；生成前替换则每轮都正确。→ 对策：只在注入前、副本上替换（ILB-5.4）。

**ILB-7.11 注入顺序不稳定会打穿提示词缓存。**
有前缀缓存的 API 按"最长相同前缀"计费/加速。若注入块顺序每轮变化，或注入位置落在消息中间，缓存从该位置起全部失效，用户按全价付费。→ 对策：ILB-4.2.1 第 8 步的三级稳定排序；默认位置选 `after_char` 而非 `in_chat`；`in_chat` 位置在设置中标注"可能降低缓存命中"。

**ILB-7.12 文本补全模式下部分能力不存在。**
`role`、部分深度语义在单字符串模式下无意义。→ 对策：ILB-5.2.2 能力探测 + 降级 + 诊断标注。

**ILB-7.13 帮助文案与实现漂移。**
改了界面忘了改说明，用户看到的是错的。→ 对策：文案 key 与元素 ID 绑定（ILB-6.4.3）；验收时逐项对照；文案变更同样进 CHANGELOG。

**ILB-7.14 导入字段遗漏导致的静默行为变化。**
漏掉 `caseSensitive` / `wholeWords` 这类字段，书不报错，但行为变了，用户只会觉得"这插件不准"。→ 对策：附录 A 每行一条测试；未知字段进 `_source.unknown`（ILB-3.3.5）。

### 7.15 手机上的横向滚动

**症状**：手机上规则列表一屏放不下按钮，必须左右滑才看得到"编辑""删除"。

**根因**：表格布局 + 固定最小宽度（`min-width: 520px`）。桌面端看着整齐，手机端直接把内容推出屏幕。

**对策**：规则与书一律用**卡片**而不是表格；所有横排容器 `flex-wrap: wrap`；宽度用 `flex: 1 1 <basis>` + `min-width: 0`，让它先缩小再换行；删除任何"为了桌面好看"的固定最小宽度。验收时用真机或 375px 宽视口检查，**不能用桌面缩窗口代替**（触屏的点击热区与滚动行为不同）。

### 7.16 快照把正文改坏

**症状**：切了几次风格，发现自己写的正文被换掉了。

**根因**：快照里存了正文，恢复时整条覆盖。

**对策**：快照只存开关（ILB-6.11.1）。恢复只写 `enabled` 与 `always`，正文、触发词、注入位置一律不动。恢复前自动备份，给一次后悔的机会。

### 7.17 重复导入产生"同一本书的两份"

**症状**：一键导入全部之后，书架上出现两本内容一样的书，名字还相同。

**根因**：用书名判断"是否已导入"。书名可重名、可被用户改，判断必然失效。

**对策**：只认 `_source.book_file`（ILB-3.6.3）；一键导入默认跳过已导入（ILB-3.6.4）；导入完成必须报告"更新/新增/保留/冲突"四个数（ILB-3.6.5）。

### 7.18 "试一句"与真实判定给出不同答案

**症状**："试一句"说会出现，实际对话里没出现（或反过来）。

**根因**：两套判断逻辑各自演化，最后谁也不知道哪套是对的。

**对策**：`previewEntry` 必须复用 `evalTrigger` 与 `evalWhenArray`（ILB-4.9.2），且明确不做概率/同组/预算/连锁（ILB-4.9.3）。预演与正式判定的差别必须写进界面文案，而不是让用户自己猜。

### 7.19 判定流程的三种"以为坏了"

**症状一**：用户画了流程，规则反而不出现了。
**根因**：默认 `mode: "and"`，关键词与流程是**并且**关系；用户以为流程会取代关键词。
**对策**：想只用流程就切到 `only`（ILB-4.10.7），并在编辑器里写清楚两者关系。

**症状二**：判断不成立后什么都没发生。
**根因**：「不成立时」留空 = 整条流程不通过（ILB-4.10.4）。
**对策**：这句后果必须印在「不成立时」那一块里；想"不成立也继续"就放一个「通过（结束）」节点，而不是留空。

**症状三**：变量总是空的。
**根因**：变量拼写不一致，`define` 写的是 `mood`、`compare` 读的是 `mode`，而读不存在的变量按空值处理，不报错。
**对策**：变量名在界面上用输入框而不是自由文本下拉；执行步骤里显示"定义 mood = …"，让拼写差异肉眼可见。

**共同的对策**：流程的每一步都进 `steps`，"试一句"和诊断页都要显示出来（ILB-4.10.10）。

**ILB-8.0** ✅ 顺序不可调。v1 把注入层放在第 3 阶段是错的：整个产品成立与否押在"能不能干净地把内容塞进那一次请求"上，这件事必须最先被证伪或证实。

**结论**：Phase 0 探针仍未执行，第 3 节（注入）与第 6 节（界面）不得据此宣称已通过。按 ILB-8.0 的顺序，Phase 0 没过之前不进入 Phase 6 的加固结论。

**ILB-8.0.3** 🔧 **入口文件必须被检查（v2.5.2 补，来自一次真实事故）**：2026-10-24 推送的 v0.4.4 里，`index.js` 因为一次错误编码的文本替换而变成乱码，并且吃掉了一个引号，`node --check` 报 `SyntaxError: missing ) after argument list`。后果不是"某个功能坏了"，而是**整个扩展不加载**：悬浮球、设置卡片、面板全部消失。而当时的检查全部通过——因为 `tests/linkcheck.mjs` 明确跳过了 `index.js`（理由：它是自启动入口，导入就要宿主与 DOM）。
教训写成硬约束：
1. **任何"检查所有模块"的脚本不得跳过入口文件**。入口有语法错误时，扩展连一行都不会执行，用户看到的是"什么都没发生"。
2. 入口的检查方式：给它一个最小的 `document` 桩，让 `document.readyState === 'loading'`，于是 `start()` 只会挂到 `DOMContentLoaded` 上、不会真的启动；这样既能解析、又不会误启动。
3. **检查项的价值 = 它覆盖的失败面**。"通过 37 项"如果少了一项是入口，那这一项的权重高于其余 36 项之和。
4. **禁止用 `Get-Content -Raw`（默认编码）+ `Set-Content -Encoding utf8` 修改含中文的源码**：前者在 Windows PowerShell 下按 ANSI/GBK 解码，后者按 UTF-8 写回，等于把整份文件转码一遍，字节数变化还会吃掉引号。改源码一律用能保持 UTF-8 的编辑器级操作。

**ILB-8.0.2** 🔧 **探针必须回答的四个新增问题（v2.1.1 补）**：
1. `host.js` 的多候选路径在实际安装位置下命中哪一个？`via` 字段要打印出来。
2. 改一次设置、等两秒、刷新页面，改动还在不在？——检验 `saveSettingsDebounced` 落盘是否真的生效（D-0018）。
3. `setExtensionPrompt` 的 `position`/`depth`/`role` 三者在**文本补全**与**聊天补全**下分别产生什么可见效果？——这是注入层唯一的真实依据。
4. 注入之后，`chat` 与 `chatMetadata` 有没有被改动？——这是 ILB-1.2.1 的机器验证。

### 10.0 定位：记忆，不是事件驱动器（v0.7.1 / D-0043）

**一句话**：这个模块产出的是"角色此刻确定的状态"，以及让模型别再口胡的那段摘要；它不是玩法引擎，也不是游戏。

它只做四件事：

1. **认出承诺**：从正文里读 `[[ILB:获得:铜钥匙]]` 这类标记（模型写，或用户补记）；
2. **把承诺变确定**：用用户声明的变量、约束、规则做校验与计算，不成立就整条拒绝并写明原因；
3. **把确定的状态交回给模型**：注入一段账本（含"本轮变化"），让下一轮以它为准；
4. **把状态开放出去**：条目、规则、界面可以读它、改它（界面修正与组合面见 §10.12）。

明确**不做**：

- 不做事件级联/调度器/节点图（`emit`、事件队列、深度与循环控制一律不引入）；
- 不做玩法模板：预设只是示例，产品不预设世界、剧情、职业、战斗；
- 不做可视化编程（在组合面稳定前）；
- 不让 AI 自由决定状态——那是要消除的问题，不是要增加的能力。

**"涌现"从哪里来**：从"条目触发逻辑（触发词/概率/分组/时效）× 状态条件 × 状态写入 × 界面修正"的组合来，而不是从新引擎原语来。详见 §10.12。

> 历史说明：v0.7.0 曾按"事件驱动器"方向讨论过 v0.8 的 emit/事件图/Blueprint 路线；该路线在 v0.7.1 被否决（D-0043），不作为待办。

### 10.2 四层模型与三条纪律

- **ILB-10.2.1** ✅ 四层全是声明、加玩法不改核心：**实体目录**（有什么） / **状态变量**（记什么） / **约束**（什么算合法） / **规则**（事实如何改变状态）。
- **ILB-10.2.2** ✅ AI 只写事实，不写机制：标记里只有动词与对象，没有类型、数值、平衡；数值、容量、上限由声明决定。
- **ILB-10.2.3** ✅ 状态由**重放**得到：`状态(第 N 条) = fold(消息 1..N)`。滑动、重生成、删消息、刷新都只是重算；不需要版本号，也不会出现账本与对话不一致。
- **ILB-10.2.4** ✅ 能算的都不许存：剩余格、总重量、是否满、关系条目数一律由 `derive()` 计算。
- **ILB-10.2.5** ✅ 原子拒绝且可见：一条事实要么整条生效，要么完全不变；拒绝必须带原因并显示；解析不出的标记进 `unknowns`，不许静默丢弃。
- **ILB-10.2.6** ✅ 规则的触发条件只看**这条事实发生之前**的状态；同一条事实里，前面规则改出的值不许把后面的规则带起来（否则规则表的书写顺序会改变语义）。
- **ILB-10.2.7** ✅ 声明写错（引用不存在的变量、不认识的 `op`/`on`、没有效果的规则）在**编译期**进 `problems`，不在运行期静默跳过。

### 10.3 事实语法

- **ILB-10.3.1** ✅ 定界符是 `[[ILB:…]]`，**不与 SillyTavern 的 `{{…}}` 混用**（其它扩展也在注册宏）。
- **ILB-10.3.2** ✅ 八个动词：`获得` `失去` `使用` `关系` `地点` `标记` `解除` `见过`。数量的写法是 `对象×N`；关系的写法是 `人物/方向+1`；地点的写法是 `从/到`。
- **ILB-10.3.3** ✅ `tick` 不是模型写的：每条消息末尾由引擎自动发一次，用于"冷却 N 轮"这类递减。
- **ILB-10.3.4** ✅ 解析失败保留原文进 `unknowns`，带 `code` 与 `hint`（例如"认不出「拿到」，可用的有：…"），由上层显示。

### 10.4 声明字段（`narrative/preset.js` 是内置样本）

- **ILB-10.4.1** ✅ 类型只有六种：`text` `number` `flag` `list` `map` `enum`；`list` 可声明 `of`（目录类型）与 `unique`（去重）。
- **ILB-10.4.2** ✅ 约束五种：`max`（格数）、`sumMax`（按目录 `weight` 求和）、`range`（数值范围）、`mutex`（开关互斥）、`require`（条件前置）。
- **ILB-10.4.3** ✅ 效果九种：`add` `remove` `set` `inc` `dec` `mapInc` `mark` `unmark` `reject`。`reject` 是玩法规则主动拒绝（"药水还在冷却"），比"没有规则匹配"更明确。
- **ILB-10.4.4** ✅ 条件字段：`name` `tags`（查目录）`dir` `from` `to` `all`（变量比较）`not`。变量引用：`$name` `$count` `$sign` `$amount` `$target` `$from`。

### 10.9 自定义状态操作与动词别名（v0.7.0，v0.7.1 改名）

> v0.7.1 起，这里说的"事件"不再具有"发出事件、排队、级联"的含义；它只是给一类状态变化起名字（D-0043）。字段名 `events` 暂不改（避免破坏已保存的声明），文档与界面一律解释为"自定义状态操作"。

- **ILB-10.9.1** ✅ 声明顶层新增两个可选字段：`events`（数组，元素 `string` 或 `{id, label}`）与 `verbs`（对象，别名 → 八个内置动词之一）。解析层先查内置，再查别名，最后查自定义事件；同名以内置/别名优先，重复的自定义事件忽略。

### 10.12 组合面：和已有条目/规则/界面互动（v0.7.1 起的重点）

这是"复杂来自组合"的落点。**不新增引擎原语**，只把状态接到已有模块上：

| 方向 | 接口 | 状态 |
|---|---|---|
| 账本 → 条目 | 条目内容/条件可读状态；宏（如 `{{ILB:生命}}`）在条目里展开 | 已做（v0.8.0：宏读聊天变量；账本本身已移出） |
| 条目 → 账本 | 条目激活时"声明式地"应用一条事实（entry hook），或条目正文/作者注释里写标记 | 部分已做（v0.8.0：`remember` 写变量、`activate` 拉条目；事实标记随账本移出） |
| 账本 → 规则 | 规则条件里可引用状态（`when.all` 已有变量比较）；不新增表达式语言 | 部分可用 |
| 账本 → 提示词 | 注入摘要 + 本轮变化 | 已做（10.8/10.10） |
| 界面 → 账本 | 手动修正 / 补记 / 撤销（带审计） | 未做（§10.7 待定） |
| 现有判定链 | 触发词、概率、分组择一、时效、预算——保持原样，由状态条件去组合它们 | 已存在，不改语义 |

**边界**：组合面只允许"读状态 / 写一条声明过的事实 / 在条目里展开一个只读值"三类动作；不提供脚本、循环、递归。复杂逻辑仍由用户在声明里写规则，工具只负责把它们接起来。

### 10.13 明确不做（v0.7.1 起）

- 事件级联：`emit`、事件队列、深度/循环调度、因果图执行（D-0043）。
- 玩法/世界模板：职业、战斗、副本、配方等预设内容不进产品；`preset.js` 只是语法示例。
- 可视化编程（Scratch/节点图/Blueprint）：不做。
- 表达式语言或脚本钩子：不做（保留 D-0006 红线）。
- 用 AI 直接改状态：不做（只接受事实标记 + 用户声明 + 界面修正）。

### 10.14 聊天变量与宏（v0.8.0）

变量是"让条目依赖的东西"的最小实现：一个聊天一张表，存"名字 → 值"，有类型、可读写、可删除，**只对当前聊天生效**。

- **ILB-10.14.1** ✅ 唯一实现在 `extension/core/vars.js`（纯计算，无 DOM）：`normalizeVars`、`coerceValue`、`readPath`、`displayValue`、`expandMacros`、`macroNames`、`missingMacros`、`resolveChatId`。别处只调用它，不各自解析。
- **ILB-10.14.2** ✅ 值形状固定为 `{ type: 'number' | 'text' | 'bool', value }`。数字允许 `5`、`'5.5'`、`'5hp'`（前缀解析）、空串（视为未定义）；布尔接受 `true/false/是/否/开/关/1/0`。显示时数字去掉多余小数，文本照原样。
- **ILB-10.14.3** ✅ **删除 ≠ 回到默认值**：删掉一个变量就是"未定义"，宏原样保留 `{{ILB:名字}}`，条目不展开、不报错；`missingMacros` 负责列出没解析成功的名字（诊断/界面可提示）。
- **ILB-10.14.4** ✅ 宏语法 `{{ILB:名字}}`，只读，在**条目正文被激活时**展开成当前值；支持 `a.b` 形式读嵌套字段（`readPath`）。宏不能出现在触发词里，也不支持表达式、算数、函数调用（守住 D-0006 红线）。
- **ILB-10.14.5** ✅ 持久化位置：`extension_settings[namespace].chatStates[chatId].__vars`（repository 的 `getVars / mergeVars / deleteVar`）；`chatId` 缺失时统一落到 `'default'`。不写顶层的 `vars`，避免把聊天变量变成全局设置。
- **ILB-10.14.6** ✅ 写入来源只有两类：流程图里的「记住」节点（§10.15），以及别的扩展通过 `globalThis.ILB.vars.write()` 这类接口写入（对外接口见 §10.16）。**AI 永远不能直接改变量**——它只能写事实标记（若账本模块重新装上）或由用户/扩展决定。
- **ILB-10.14.7** ✅ 面板新增一页「状态」：列出当前聊天的全部变量，可新增、改值、删除；空列表时给一句"这个聊天还没有变量"的说明，不显示假数据。

### 10.15 流程节点「记住」「激活条目」（v0.8.0）

这两个节点把条目逻辑和状态接起来，是"有限连锁"的第一个落点；它们仍然走 §5 的流程判定，不引入脚本。

- **ILB-10.15.1** ✅ 「记住」：字段 `name`（变量名）+ `value`（操作数，可写死数字/文本/布尔，也可引用另一个变量）。节点成立时把值收进"本轮待写入"，**不立刻改状态**；整轮判定结束后才由 pipeline 一次性落盘。因此被拒绝/中断的一轮不会留下半个状态。
- **ILB-10.15.2** ✅ 「激活条目」：字段 `entryId`，下拉里只列同一本书的条目，id 形如 `书id::条目id`。被激活的条目**绕过触发词**直接进入本轮候选，随后仍受"启用、预算、每轮上限、去重"约束；被激活的条目自己的流程也会照常执行。
- **ILB-10.15.3** ✅ 鲁棒性：`entryId` 为空、条目不存在、条目已关闭时，只写一条诊断（stage `activate`，passed=false），不让这一轮失败；同一个 id 在一轮里被激活多次只算一次。
- **ILB-10.15.4** ✅ 写入只来自"本轮真正激活成功"的条目：没进内容、被流程否决的条目不写；写入合并冲突时后写覆盖前写，并记一条诊断。
- **ILB-10.15.5** ✅ 编辑界面（`ui/flow-editor.js`）为两种节点提供表单：记住 = 名字输入 + 值输入（复用操作数编辑）；激活 = 条目下拉。存储结构沿用 `entry.logic.nodes[]`，字段名不变。
- **ILB-10.15.6** ✅ 「计算」节点默认只把结果放进**本轮**的变量副本（临时值，供后面的判断用），不写回聊天；勾上「存进聊天」（`persist: true`）才进入待写列表，和「记住」一样在整轮判定成功后一次性落盘。给"抽卡次数 − 1"这类需要跨轮记账的场景用（`tests/gacha-demo.mjs`）。

| `uid` | `_source.uid` | 存溯源 | 不直接当 `id` 用 |
| `vectorized` | 忽略 | 记警告 | v1 不支持语义匹配 |
| `automationId` / 其他未知 | `_source.unknown` | 原样暂存 | 导出时还原 |

## 附录 C · 术语（人话版）

- **条目**：一条设定。只有它的正文会出现在对话里。
- **触发词**：让这条设定"想起来"的词。
- **同组**：几条设定争一个位置，只出最具体的那条。
- **权重**：越具体、越该优先的，数字越大。
- **连锁**：一条设定里出现的词，可以带出另一条设定。
- **时效**：出现一次之后，接下来几轮里它还在 / 暂时不能再出现。
- **预算**：每轮最多允许塞进去多少字，超了就从最不重要的开始丢。
- **零注入**：这一轮什么都不加，但对话照常继续。

**一句话总结**：数据层只负责"存和搬"，判定层只负责"该出哪几条"，注入层只负责"放进这一次请求"。三层之间只传 `EvalRequest` 与 `ActivationResult`。任何一层出错都退成零注入，绝不让用户的生成挂掉。原生世界书只在导入时被读一次，此后永不触碰——**但角色卡上说"这本书属于这个角色"这句话，我们要看。**
