# 决策记录

**这是什么**：每一条"换了做法"的决定，都在这里有一份留底。它回答的不是"现在怎么做"，而是**"当时为什么这么做、否决了什么"**。

**规则**：

- 只追加，**永不改写已生效的条目**。
- 决策被推翻时，旧条目状态改为 `已被 D-xxxx 取代`，并新写一条说明为什么推翻。**不改原文。**
- 编号 `D-xxxx` 唯一，不复用。
- 每条必须写"否决的方案"和"否决的理由"，否则这条记录没有价值——只记结论的决策记录，等于没有。

## D-0001 · 数据层与判定层严格分离

- **日期**：2026-10-23
- **状态**：✅ 生效
- **提出者**：用户

**背景**

用户对结构的描述是：「数据存储真的就只是数据存储，它和逻辑部分是不耦合的……逻辑部分就是触发器以及执行器，数据库就只是文件夹里的不同文件。」

**决定**

数据层不包含任何规则，判定层不 import 数据层的模块。两者之间只传一份条目清单（`Book` 快照）。

**否决的方案**：把判定规则写成条目的一部分（例如每条自带一段可执行脚本）。
**否决理由**：规则一旦跟着数据走，改规则就等于改数据，改一个判定逻辑要遍历所有条目；而且数据文件变成可执行内容，来源不可信时无法安全加载。

**后果**：正面——判定层可以脱离 SillyTavern 单测，这是整个项目最值钱的一条工程属性。负面——条目的"规则感"要靠界面补齐（→ ILB-6.2 规则表），否则用户面对一堆字段不知所措。

## D-0002 · 允许只读角色卡的绑定字段

- **日期**：2026-10-23
- **状态**：✅ 生效（取代 v1 的 A1 全禁做法的对应部分）

**背景**

v1 的公理 A1 要求"运行时零依赖原生世界书"，连带禁止了读取角色卡上的世界书绑定。用户的目标是"低门槛"，而原条款的后果是：**每换一张角色卡，都要手动去选一次书。**

**决定**

允许只读 `characters[id].data.extensions.world` 用于自动选书（ILB-1.3.2）。读取失败静默回退手动，并在界面标注。

**否决的方案**：坚持零读取，全手动选书。
**否决理由**：这是把一个"数据读取"问题当成了"架构污染"问题。读一个字段不会让 ILB 依赖 `world-info.js` 的内部逻辑，也不会在升级时崩。用低门槛换一个并不存在的风险，不划算。

**后果**：若将来 SillyTavern 改了卡片结构，此适配器失效——所以它必须**可失败**，失败后手动选择继续可用。

## D-0003 · 一次性转换，而非运行时读取原生格式

- **日期**：2026-10-23
- **状态**：✅ 生效

**背景**

用户提出两种都可以：把原生书"转换"成新格式，或者"让新世界书能识别原生格式并直接当数据用"。

**决定**

只做前者：导入时一次性转换，之后与原生文件无关（ILB-3.3.2）。

**否决的方案**：运行时直接读原生 JSON。
**否决理由**：原生格式是移动靶（v2/v3、每版加字段）。直接读等于让自己的行为随别人的升级而变，而且坏得**没有声音**——书不报错，只是某些条目不再触发。另外，原生结构里没有"条件""连锁""时效"的容身之处，硬塞会变成寄生。

**后果**：用户需要执行一次"导入"动作。用信任三原则（D-0008）和导出功能（ILB-3.3.8）来降低这个动作的心理成本。

## D-0004 · 用「组 + 权重」表达组合特化，不引入新语法

- **日期**：2026-10-23
- **状态**：✅ 生效
- **提出者**：用户

**背景**

用户想要："满足一个触发词的同时还可以设并行触发词，触发两个并行触发词可以出另一条。"

**决定**

不新增语法。用"同组只出一条 + 权重越高越优先"表达 A / A+B / A+B+C 的层层特化（ILB-6.2.4）。

**否决的方案**：引入"规则链"语法（`if A and B then ... else if A then ...`）。
**否决理由**：可读性上去了，可理解性下来了。同组+权重只需要用户理解"更具体的那条优先"，这是日常直觉；`if/else` 要求用户理解短路求值和顺序依赖。

**后果**：用户必须手动把三条放进同一组。界面必须能"一键建组"，否则这个设计反而更麻烦。

## D-0005 · 连锁触发作为涌现机制

- **日期**：2026-10-23
- **状态**：✅ 生效

**背景**

用户的原话：「我想要的就是一个由基础功能能够涌现出比较复杂功能的模块。」

组合条件再多，复杂度也是平面的——用户要穷举"还有哪几种组合"。真正能让复杂度自己长出来的机制是：**已激活条目的正文，可以继续触发别的条目**。

**决定**

实现连锁触发（ILB-4.6）：匹配文本按层累积，默认 3 层，同一轮内每条只激活一次，`chain.participate` 可单条关闭。

**否决的方案**：只做组合条件，不做连锁。
**否决理由**：组合条件是"用户预先想好所有情况"，连锁是"系统自己串起来"。用户要的是后者。

**后果**：正面——三条互不相干的条目能长出一条因果链，作者不需要写任何接线。负面——可能上下文爆炸（→ ILB-7.9）与结果不可预测（→ 用诊断展示连锁路径，ILB-4.6.5）。

## D-0006 · 废弃表达式语言，改为条件卡片

- **日期**：2026-10-23
- **状态**：✅ 生效（废弃 v1 §4.3）

**背景**

v1 设计了受限的表达式 AST（`+ - * / == != && ||`、`countMatches()` 等），并称"这既是为了安全，也是为了让表达式在 UI 里可以被可视化编辑"。

**决定**

整段废弃（ILB-4.4.1）。改为三种固定卡片（`contains` / `activated` / `var`）+ 两种连接词（`all` / `any`），由界面生成，用户不可直接编辑语法。

**否决的方案**：保留 AST，用可视化编辑器包一层。
**否决理由**：一个可视化编辑器只要支持任意表达式，就一定会退化成"代码输入框 + 语法高亮"。用户最终还是要理解"变量引用""运算符优先级"。这与"低门槛"直接冲突。**能砍的语法就该砍掉，而不是给它做一层壳。**

**后果**：表达能力下降（例如无法写 `countMatches(a) * 2 > b`）。已接受：v1 不需要这种能力，真要时再走决策流程扩展卡片类型。

## D-0007 · 注入主路径改为 `setExtensionPrompt`

- **日期**：2026-10-23
- **状态**：✅ 生效（废弃 v1 §5.1 路径 A）

**背景**

v1 把 `llm/stream` 列为"推荐主路径"，把 `CHAT_COMPLETION_PROMPT_READY` 列为兼容路径。

**决定**

主路径改为 `context.setExtensionPrompt()`（ILB-5.1.3），并保留 `generate_interceptor` 与 `CHAT_COMPLETION_PROMPT_READY` 作为降级选项，全部通过 `InjectionSink` 抽象接入。

**否决的方案**：按 v1 原样实现两条路径。
**否决理由**：
1. `llm/stream` 在 SillyTavern 的公开事件列表里找不到对应项，很可能是记错的名字。把不存在的钩子当主路径，Phase 3 会直接卡死。
2. `setExtensionPrompt` 是长期存在的正式扩展接口，天生满足"注入但不进 chat"，且自带深度与角色参数——它本来就是这个问题的最优解，v1 却没提它。
3. v1 自己也承认 `CHAT_COMPLETION_PROMPT_READY` 的可写性不确定。把不确定的东西当备胎可以，当主路不行。

**后果**：`setExtensionPrompt` 以 key 为单位管理注入，多条内容需要合并成一个字符串——顺序稳定性因此更重要（ILB-4.2.1 第 8 步）。**此决定依赖接口存在性验证**，由 Phase 0 探针证伪；证伪则回退到 interceptor。

## D-0008 · 导入信任三原则

- **日期**：2026-10-23
- **状态**：✅ 生效

**背景**

v1 只说"导入是单向的、一次性的、可重复执行的"，没有规定对源文件的处置。

**决定**

1. 只读源文件，绝不删除/改写/移动；
2. 源文件原始字节另存一份到 `data/imports/`；
3. 导入永不自动删除 ILB 已有条目。

**否决的方案**："导入后把原生书清空/替换"，以保持两边一致。
**否决理由**：用户判断一个插件是否可信，看的是第一次点击时有没有毁掉他的东西。一旦发生过一次数据丢失，无论后续怎么解释，这个插件都不会再被信任。**让用户敢点，比让两边干净重要得多。**

**后果**：可能出现"原生书和 ILB 书内容分叉"。接受——这是用户自己的选择，界面上明说即可。

## D-0009 · 常驻条目分类器改为「体检」

- **日期**：2026-10-23
- **状态**：✅ 生效（废弃 v1 §3.4 的待复核队列）

**背景**

v1 设计了一个"保守的、召回优先的分类器"，把可疑的常驻条目抽到待复核队列里标红让人工处理。它同时断言"自动把自然语言规则转成可执行条件是不可靠的"。

**决定**

诊断保留，队列取消。改为用户主动点击的「体检」，产出**建议卡片**让人一条条接受/忽略；可调用模型生成建议，但永不自动改数据、永不进入生成路径（ILB-6.7）。

**否决的方案**：按 v1 原样做关键词启发式 + 复核队列。
**否决理由**：
1. 中文里"如果""当"到处都是，关键词启发式的准确率不足以支撑一个队列；错标会让用户对整个功能失去信任。
2. 队列把工作推回给用户，而用户的诉求恰恰是"少动脑"。一条条判定 30 个条目，比不装这个插件还累。
3. v1 断言"自然语言转条件不可靠"——这在**没有大模型**的年代成立。现在可以用宿主自带的静默生成 + 结构化输出先做一次转换，再由人确认。"不可靠"从"不能做"降级为"需要人复核"，而这正好是卡片的形态。

**后果**：体检需要调模型时有 token 成本 → 只在用户点击时运行，并提供纯规则兜底模式。

## D-0010 · 未知字段无损暂存

- **日期**：2026-10-23
- **状态**：✅ 生效

**背景**

原生条目有几十个字段，v1 的映射表只覆盖了 9 个。

**决定**

映射表覆盖主流字段（附录 A，22 行）；**映射表之外的一切字段原样存入 `_source.unknown`，导出时尽量还原**（ILB-3.3.5）。

**否决的方案**：只保留已知字段，其余丢弃。
**否决理由**：用户无法预知哪个字段对他重要。丢弃是**不可见**的损失——书能导入、能跑，但某些行为悄悄变了。相比之下，多存一点键值对的成本可以忽略。

**后果**：`_source.unknown` 会随导出/导入传递，可能出现陈旧的冗余字段。接受。

## D-0012 · 数据存进 `extension_settings` 的独立命名空间，而不是 `data/` 目录

- **日期**：2026-10-23
- **状态**：✅ 生效（修订 v2.0.0 的 ILB-3.1）

**背景**

v2.0.0 规定数据存在扩展目录下的 `data/`，写入用"临时文件 + 改名"保证原子性。这个方案在浏览器里跑不通：**SillyTavern 的第三方前端扩展没有服务端写文件权限**。它只能调用宿主已有的接口，而这些接口不提供"往某个任意目录写文件"的能力。

**决定**

保持"扩展自己的命名空间、绝不碰 `worlds/`"这个原则不变，改变物理落地：数据序列化进 `extension_settings.independent_lorebook`，由宿主负责落盘与原子写入；另提供整库导出为单个 JSON 文件。

同时加一条硬约束：**所有存储访问必须经 `BookRepository` 端口**，禁止模块直接读写 `extension_settings`。

**否决的方案 A**：放弃功能，等宿主提供目录写入。
**否决理由**：需求不会等基础设施。而且"存进设置"在数据安全上并不更差——`settings.json` 本来就在用户数据目录里，跟着用户走、跟着备份走。

**否决的方案 B**：存在浏览器 IndexedDB。
**否决理由**：清缓存就没了。这类"我配了三小时的书突然消失"的事故，对一个以"让人敢用"为目标的插件是致命的。

**后果**：书存在 `settings.json` 里，书很大时会让这个文件变大（典型世界书 10–500 KB，可接受）。导出功能因此从"可选"升级为"必须好用"——它是用户唯一的逃生舱。

## D-0013 · 书是分组，但不是唯一的调用单位

- **日期**：2026-10-23
- **状态**：✅ 生效（新增 ILB-3.5）
- **提出者**：用户

**背景**

用户的原话：「像原生世界书一样，能够根据不同的角色卡以及不同的情况，选择性触发某些世界书……每个世界书都是一个分组，但除了通过分组进行调用，整个逻辑部分也能从所有世界书的总条目池中进行调用。」

**决定**

给每本书两个**互相独立**的开关：`activation.mode`（怎么启用）与 `pool.share`（条目是否进全局池）。本轮条目池 = 已启用书的条目 ∪ 池共享书的条目。

**否决的方案**：只做"按书启用"，让规则只能在书内部生效（即 v2.0.0 的 ILB-4.4.5 那样限制同书引用）。
**否决理由**：现实里书的划分是按**来源**（这本是别人写的、这本是我自己写的），而不是按**用途**。文风书里想引用设定书的一条，是完全正常的诉求；限制同书引用等于逼用户把所有东西塞进一本书，那就退回了原生世界书的处境——一个巨型条目列表。

**否决的方案**：一个开关同时管"启用"和"入池"。
**否决理由**："我想让规则能引用它，但不想它整本自动注入"是最常见的需求。合并开关就无法表达，用户只能二选一，两边都不对。

**后果**：界面多两个控件，但都在书架的一行里，理解成本低。默认 `pool.share: false`，所以新用户不会被第三方书的互引撑爆预算（→ ILB-3.5.6）。

## D-0014 · 用"端口 + 注册表"做解耦，而不是靠约定

- **日期**：2026-10-23
- **状态**：✅ 生效（新增 ILB-2.4 / ILB-2.5）
- **提出者**：用户

**背景**

用户的要求：「整个项目的代码一定要足够低耦合度，以便后续的更新或者维护。每个模块只管自己的事情，以后如果新增什么功能，只需要通过预留的接口或者类似渠道被调用。这样，就算坏，也不至于整个项目一起崩溃。」

**决定**

1. 每个外部依赖都藏在"接口 + 默认实现"后面（`BookRepository`、`InjectionSink`、`HostBridge`、`BookActivationProvider`、`RulePolicy`）。
2. 整个扩展**只允许一个文件** import 宿主的 `script.js`。
3. 新增功能 = 新增一个端口实现，或向注册表追加一项；不改已有模块。
4. 每个处理器独立 try/catch，失败降级而不停机（ILB-2.5）。

**否决的方案**：靠"模块划分清楚 + 代码风格统一"来保证解耦。
**否决理由**：约定不会在三个月后还被人记得。能检查的约束才能活下来——"只允许一个文件 import 宿主"是可以 `grep` 出来的，而"注意分层"不是。**把架构变成一条能被机器检查的规则，它才会真的存在。**

**后果**：多一层间接（例如要写 `BookRepository` 接口和一个默认实现才能读一本书）。这个成本在第一天就付，换来的是：换存储、换注入通道、换判定策略都不用动别的模块，以及每个模块都能在没有宿主的环境里被单独测试。

## D-0011 · 帮助文案外置 + 默认值保守策略

- **日期**：2026-10-23
- **状态**：✅ 生效
- **提出者**：用户

**背景**

用户要求：「每个页面添加一个针对该功能的比较醒目的提示按钮，点击后给出对应的讲解。」关于默认值，用户明确表示：「默认设置不可能让所有用户都觉得好用，我们也没有能力做市场调研……只能在其他方面进行补齐。」

**决定**

1. 每个面板/复杂控件区必须有醒目 `？` 按钮，原地弹三段式浮层（这是什么 / 影响什么 / 一个例子）；文案存 `data/help/<locale>.json`，与元素 ID 绑定；**没有文案视为功能未完成**（ILB-6.4）。
2. 默认值一律保守（ILB-6.5.1），失败方向偏向"不注入、不启用"，并在帮助浮层里写清"为什么默认是这个""什么时候该改它"。
3. 明确不追求"最合适的默认值"，追求"每个默认值都能被解释"。

**否决的方案**：把默认值调成"功能全开"，用丰富度换好感。
**否决理由**：默认全开意味着新用户第一轮就被塞进一堆没预期的设定，出问题时不知道该关哪个。保守默认 + 显式解释，用户至少知道自己站在哪。

**后果**：一部分用户会"用不出效果"就放弃 → 用三步引导（ILB-6.6）与体检报告（ILB-6.7.5）兜住。

## D-0015 · 判定结果带三个"只给界面看"的附加字段

- **日期**：2026-10-23
- **状态**：✅ 生效（新增 ILB-4.1.5）

**背景**

写 `core/evaluate.js` 时发现：诊断面板需要回答"为什么没出现"，而最常见的两个答案是"被预算挤掉"和"这本书这一轮根本不在场"。这两件事如果需要界面自己再算一遍，就要把预算公式和 `resolveBooks` 的判定逻辑复制到界面层。

**决定**

`ActivationResult` 除规范字段外，附带 `budget: {limit, used, dropped}`、`books: {active, inactive, reasons, warnings}`、`poolSize`。明确约束：**注入层不得读取这三个字段**；删掉它们不得改变注入结果。

**否决的方案**：界面自己重新计算预算和在场书。

## D-0018 · 宿主路径用"多候选 + 合并"，落盘由装配层负责

- **日期**：2026-10-23
- **状态**：✅ 生效（实现细节，修订 `host.js` 与 `adapters/repository.js`）

**背景**

对照 SillyTavern 内置扩展 `public/scripts/extensions/expressions/index.js` 的真实 import 头部，发现两件事：

1. 内置扩展写 `'../../../script.js'`（从 `extensions/<名字>/` 出发），但第三方扩展在 `extensions/third-party/<名字>/`，深一层，正确路径是 `'../../../../script.js'`。照抄内置扩展的相对路径，会指向一个不存在的文件，然后被 `catch` 静默吞掉。
2. `getContext` 事实上由 `public/scripts/extensions.js` 导出，内置扩展正是从 `'../../extensions.js'` 拿的。
3. 更严重的一条：`extension_settings` 只存在于内存，宿主不会自动发现变化并写盘，必须由扩展调用 `saveSettingsDebounced()`。原 `repository` 只改对象，等于"界面里改的东西刷新就消失"。

**决定**

1. `host.js` 依次尝试多个候选路径（`'../../extensions.js'`、`'/scripts/extensions.js'`、`'../../../../script.js'`、`'../../../script.js'`、`'/script.js'`），**不因某个路径成功就返回**，而是把所有成功的模块放在一起，按字段挑选可用实现（`getContext` 优先来自 `extensions.js`，事件与请求头来自 `script.js`）。
2. `host.js` 额外暴露 `saveSettings()`，内部包装 `saveSettingsDebounced`（找不到时退回 `saveSettings`），返回布尔值、从不抛。
3. `repository` 接受可选的 `persist` 回调，每次写操作后调用一次；`index.js` 负责把它接成 `host.saveSettings`。**只有装配层知道"怎么落盘"**，数据层不 import 宿主（符合 ILB-2.4）。

**否决的方案**：在 `repository` 里直接 import `script.js` 调 `saveSettingsDebounced`。
**否决理由**：那样"唯一允许 import 宿主的文件"这条约束就破了，而这个约束正是 ILB-2.4 的检查依据。

**否决的方案**：只写一个正确路径，不做候选。
**否决理由**：宿主目录结构在历史版本里变过，而扩展被装在 `public/scripts/extensions/` 下的情况（非 third-party）真实存在。多候选的成本只是几次失败的动态 import，是一次性的。

**后果**：`saveSettingsDebounced` 是去抖的（延迟数百毫秒）。如果用户在界面里改完立刻刷新页面，最后那次改动仍可能丢。界面上的保存提示要如实说明，不能宣称"已保存"。

## D-0020 · 布局判定放进纯函数，而不是只写 CSS 媒体查询

- **日期**：2026-10-23
- **状态**：✅ 生效（`ui/layout.js`、`tests/ui-layout.test.mjs`）

**背景**

要求是"针对 PC 和手机分别修改 UI"。最省事的做法是写两组 `@media` 查询，让 CSS 自己变。但浮窗是**可以被拖动、被缩放**的：它的坐标和尺寸由 JS 记住，下次打开要还原。CSS 媒体查询回答不了"上次用户把窗拖到了 (1300, 700)，现在屏幕只有 1000px 宽，应该收回到哪"。

**决定**

1. 一切"算位置"的逻辑放进 `ui/layout.js`，纯函数、不碰 DOM：`pickLayout`、`defaultWindowGeometry`、`clampGeometry`、`defaultFabPosition`、`clampFabPosition`。

3. CSS 只负责外观（整屏、间距、安全边），不负责决定坐标。
4. 为这些纯函数写测试（`tests/ui-layout.test.mjs`），因为算错的表现是"窗口跑到屏幕外"，肉眼很难在日常使用中发现。

**否决的方案**：只写 CSS 媒体查询，窗口位置全部交给 CSS 默认值。
**否决理由**：放弃"记住上次位置"这个能力；而且换屏幕尺寸后无法把窗口收回可视区。

**否决的方案**：在 `ui/floating.js` 里就地做这些计算。
**否决理由**：那样就没法测了——要测就得在无浏览器的环境里跑，而 `floating.js` 一 import 就会碰 `document`。

**否决的方案**：按浏览器 UA 判断手机。
**否决理由**：UA 会被伪装、也区分不了触屏平板与桌面小窗；`innerWidth` 与 `pointer: coarse` 是当下真实条件，直接量就行。

**后果**：正面——两套布局的差异集中在一处，将来加平板专属布局只改 `pickLayout`。负面——`layout.js` 与 CSS 里的尺寸常量（`52px` 悬浮球）必须手动保持一致，已在两边注释里互相标注。

## D-0025 · 让判定"说出来"，而不是再写一套判断

- **日期**：2026-10-23
- **状态**：✅ 生效（`core/evaluate.js` 的 `previewEntry`、规格 ILB-4.9）

**背景**

用户问："通过逻辑判定来选择是否触发世界树的功能，我好像并没有看见在哪里？"事实上判定一直在跑（规则页每条规则都有触发词），但**结果不可见**：用户填了词，却没有任何地方能当场告诉他"这句话会不会让它出现、卡在哪一步"。

**决定**

1. 新增纯函数 `previewEntry(entry, options)`，顺序 `enabled → timed → always → trigger → when`，返回 `{passed, reason, steps[]}`。
2. 它**复用** `evalTrigger` 与 `evalWhenArray`，不复制判断逻辑。
3. 它明确**不做**概率、同组、预算、连锁、状态写回。
4. 界面上每条规则、以及编辑器内（用未保存的值）都能调用它。

**否决的方案**：不做预演，只靠诊断页在生成后解释。
**否决理由**：诊断页是事后的，而且要先发一条消息。用户调规则时的心智是"我现在就想知道这句话会不会让它出现"，事后解释太晚了。

**否决的方案**：在 `previewEntry` 里另写一套简化判断。
**否决理由**：两套实现一定漂移。漂移之后，"试一句"说会出现、实际不出现，用户会认为整个扩展不可信——这比没有预演更糟（ILB-7.18）。

**否决的方案**：预演也把概率、同组、预算算进去。
**否决理由**：这三项依赖真实的一轮对话（同组要看对手是谁、预算要看上下文长度、概率要看 seed），假装能预演等于给出错误答案。宁可划清界限并写在界面上。

**后果**：正面——用户第一次能"看着判定改判定"。负面——预演的结论与真实结果存在已知差异（概率/同组/预算三项），必须在界面上写清楚，否则会变成新的困惑来源。

## D-0026 · 判定流程用"树形嵌套节点"，不用连线画布

- **日期**：2026-10-23
- **状态**：✅ 生效（`core/flow.js`、`ui/flow-editor.js`、规格 ILB-4.10 / ILB-6.13）

**背景**

用户要"像可视化编程或游戏引擎蓝图那样"搭判定：选一个节点（检测/比较/计算/添加/定义），成立就往下走一种，不成立走另一种。

**决定**

1. 用**树**：每个判断节点自带 `then` 与 `else` 两棵子树，块里可以继续放节点。
2. 界面上不做拖线、不做端口、不做画布缩放：节点是卡片，分支是缩进块。
3. 节点种类固定八种（`test/judge/compare/define/calc/add/pass/fail`），不开放自定义节点。

**否决的方案**：真正的连线画布（节点 + 端口 + 拖拽连线 + 缩放平移）。
**否决理由**：手机上拖线、找端口、双指缩放都点不准；而用户心里想的是"下一步做什么"，不是"把线连到哪个口"。树形结构表达力足够覆盖"成立/不成立各做什么"，却不需要用户学习画布操作。

**否决的方案**：开放自定义节点（让用户写小段代码）。
**否决理由**：这与"低门槛、不写语法"的总目标直接冲突；而且自定义代码会把判定层从"纯函数、可测"变成"任意副作用、不可测"。

**后果**：正面——手机上能编辑、能单测、执行有上限。负面——无法表达"两个分支汇合后再一起判断"（图），只能用重复节点模拟；这是刻意用表达力换可用性。

## D-0030 · 浮层改成"统一出口 + 顶对齐 + 手机贴底"，而不是各处打补丁

- **日期**：2026-10-23
- **状态**：✅ 生效（`ui/help.js` 的 `openOverlay`、`style.css` 的 `.ilb-overlay` / `.ilb-modal`、规格 ILB-6.14）

**背景**

真机反馈：手机上点「试一句」「导入原生世界书」「导入记录」，弹层太靠上，右上角关闭按钮点不到。最初的反应是"给这几个弹层分别调一下 top"。但看代码会发现，所有次级菜单本来就共用 `openOverlay()`，问题不在调用方，在于那一处实现里 `align-items: center` 加 `max-height: 82vh` 的组合：内容一高，flex 子项不肯缩，整块向上溢出，标题栏正好被顶出屏幕。

**决定**

1. 修**共同出口**，不修调用方：容器 `align-items: flex-start` + `overflow-y: auto` + 安全区 padding，弹层 `margin: auto`。短内容仍居中，长内容从顶部开始，物理上不可能向上溢出。
2. 标题栏固定、正文单独滚动，关闭按钮用 `×` 且手机 44×44。
3. 手机（≤768px）改为从底部升起的整宽面板：屏幕越大，居中弹窗的关闭按钮越往屏幕上半部跑；贴底永远在拇指附近。
4. 浮层只允许挂在 `document.body` 上；浮窗内部有 `overflow: hidden`，`position: fixed` 在里面会被裁掉。
5. 打开时锁背景滚动，关闭时在 `closeOverlay()` 里成对解除。

**否决的方案**：给每个出问题的弹层单独加 `margin-top` / `max-height` 微调。
**否决理由**：同一个成因会在每个弹层各表现一次，补丁会散成十份；下次有人新写一个弹层，还会再犯。而"统一出口"意味着修一次、全部生效，且可以写一条结构性冒烟测试（`tests/smoke-dom.mjs` 检查 `ilb-overlay → ilb-modal-head → ilb-modal-x` 的层级）。

**否决的方案**：手机上继续居中，只把 `max-height` 调到 `70vh`。
**否决理由**：治的是症状。屏幕高度不同，"70vh 里够不够得着"仍取决于用户的手；而且内容很短时弹窗还是浮在屏幕中间偏上。

**否决的方案**：用 `position: sticky` 把关闭按钮钉在视口顶部。
**否决理由**：`sticky` 的参照是最近的滚动容器，弹层自身滚动与页面滚动混在一起时行为不可预测；固定标题栏 + 正文滚动是更简单、更容易验证的结构。

**后果**：正面——一处修完全部次级菜单，并用一条冒烟测试锁住结构。负面——手机上弹层变成底部面板，是**外观变化**（不再居中），用户需要重新适应；且"贴底 + 88vh"在横屏手机上是否过高尚未实测。

## D-0031 · "点了没反应"先量事实，不先改代码

**日期**：2026-10-24
**状态**：生效

**背景**

用户报告："点击按钮没有界面弹出，仅有无界面的导出功能能正常使用。"上一轮刚重写过浮层的定位，第一反应是"上一轮改坏了"。但先做的是**量**而不是改：用无头 Chrome 在一个干净页面里加载真实的 `style.css` 与 `ui/help.js`，分别以 390×844 与 1280×800 打开浮层，量矩形、关闭按钮位置与尺寸、`z-index`、`display`。结果两种视口**都正常**（浮层铺满视口、关闭按钮在视口内、手机 44×44）。

这说明：把所有推断都指向"上一轮的 CSS 改错了"是错的。真正的缺陷是**这类故障发生时没有任何可见证据**——用户只能说"没反应"，开发者只能猜。

**决定**

1. 先把失败变成可见事实：打开浮层打一行 `[ILB] 浮层已打开：<标题>`；量一次尺寸，异常就用内联样式兜底并警告；未捕获错误与未处理的 Promise 拒绝转成 toast。
2. 需要等宿主数据的界面先开浮层（"正在读取…"）再等待，失败把原因写在浮层里。
3. 增加一键自检（设置页「运行自检」+ `window.ILB.selftest()`），只读、结果可复制。
4. 把"用真实浏览器量布局"固化成仓库内的 `tests/browser-probe.html`。

**否决的方案**：直接再调一次 `.ilb-overlay` / `.ilb-modal` 的 CSS。
**否决理由**：没有证据说明样式是错的（测量结果反而是对的）。在没有证据的情况下继续改样式，会把"原本正确的部分"也变成不确定，并且下一轮仍然无法判断问题是否解决。

**否决的方案**：让用户自己打开控制台看报错。
**否决理由**：用户不是开发者。要求他描述控制台，等于把排查成本转移给最没有能力承担的人。自检按钮把这件事变成"点一下、复制一段"。

**否决的方案**：加一个全局的 try/catch 包住整个扩展。
**否决理由**：会把"哪一步失败了"抹平成"整个坏了"，与 ILB-2.5 的失败隔离（每一步单独捕获、只降级这一步）相冲突。

**后果**：正面——下一轮能拿到事实（自检结果 + `[ILB]` 日志），而不是再猜一轮；真实浏览器探针成为以后所有布局结论的默认做法。负面——多了一个自检入口与两处日志，属于"为排障付的常驻成本"；自检本身在 SillyTavern 主题下是否误报尚未验证。

## D-0032 · 浮层"看得见"不靠 z-index 排序，靠让开与实测

**日期**：2026-10-24
**状态**：生效

**背景**

用户自己定位到：手机上不是"没弹出"，而是**弹出的浮层被 ILB 自己的浮窗盖住了**。浮窗在手机上整屏、`z-index: 4500`；浮层原本 `4600`，只高 100。只要有任何一条规则把它压回 4000（旧缓存、主题、别的扩展），整块浮层就被吃掉。桌面上浮窗只占一角，所以同一份代码"看起来正常"。

**决定**

1. 浮层层级提到 `2147483000`（接近上限），不再依赖"比浮窗高一点"这种脆弱差值。
2. 浮层打开时，自家浮窗、悬浮球、遮罩一律 `visibility: hidden`（`body.ilb-overlay-open`），关闭时成对恢复。**用"让开"代替"比大小"。**
3. 打开后用 `document.elementFromPoint` 实测"屏幕正中谁在最上面"，被遮挡就内联提层并警告。
4. 自检把这两条单列，探针里加一个"模拟整屏浮窗"的场景。

**否决的方案**：把浮窗层级降到 3000、浮层保持 4000。
**否决理由**：仍然在赌"没有别的东西插在中间"。一旦 ST 主题或别的扩展把自己弹层放到 3000 以上，同样的故障会以更莫名其妙的形式回来。

**否决的方案**：手机上打开浮层时把浮窗关掉（调用 `close()`）。
**否决理由**：会改变状态并触发保存；用户关掉浮层后发现浮窗也没了，等于"为了看一眼菜单丢了工作台"。`visibility` 让开不改变任何状态。

**后果**：正面——浮层的可见性变成"事实"而不是"推断"，且自检与探针都能独立验证。负面——浮层开着时浮窗会消失一下（关掉后回来），属于视觉上的轻微跳动；另外这一层让开规则依赖 body 上的 class，若别的扩展重构 DOM 可能失效（所以保留 elementFromPoint 兜底）。

## D-0033 · 检查必须覆盖入口文件

**背景**：v0.4.4 推送后，用户报告"整个扩展直接出问题，连悬浮球都没有显示"。排查发现 `index.js` 被一次文本替换写成了乱码，并因字节数变化吃掉一个引号，`node --check` 报 `SyntaxError: missing ) after argument list`。SillyTavern 加载入口失败，扩展整体不启动。

**否决理由**：手工步骤不会执行。要让它在 CI 和本地同一条命令里。

**后果**：正面——入口级故障在本地与 CI 都会立刻报红。负面——`checkEntry()` 的 DOM 桩必须维持在"刚好够解析、绝不启动"的程度，桩写得太完整会让入口真的跑起来，写得太少会在解析之后误报运行期错误。

## D-0034 · 布局不能只靠媒体查询，浮层太扁必须自愈

**背景**：用户报手机上点按钮后"只有高度非常小的一排，大概只覆盖了原本顶部的几个选项按钮"，并明确"PC 端没有任何问题，只有手机端"。用户手机用的是 SillyDroid（WebView 客户端）。查下来是两件事叠加：WebView 可能按桌面宽度排版，导致 `@media (max-width: 768px)` 不成立；浮层正文在数据回来之前是空的，而桌面规则下高度由内容决定、盒子顶对齐，于是成了一条缝。

**决定**：
1. 布局判定放在纯函数 `ui/layout.js` 的 `pickLayout()`（宽度 + 是否粗指针），结果写成 `body.ilb-mobile` 类；`.ilb-mobile` 与 `@media (max-width:768px)` 是同一套规则的两个入口（"两把钥匙"）。
2. 浮层盒子有高度下限（`min-height: 160px`），打开后**实测**一次高度，低于 `min(180, 视口×0.2)` 就内联撑到 `45vh` 并告警。
3. 正文为空时插入一句人话说明，不许留空白浮层。
4. 自愈检查除两次 `requestAnimationFrame` 外，再加 400ms 定时兜底，用"只跑一次"标记合并。

**理由**：手机上的"屏幕窄"与"CSS 宽度窄"是两件事，WebView 会骗媒体查询；而"样式没生效"是用户端最常见的失败（旧缓存、主题覆盖），代码无法保证它不发生，只能保证它发生时界面仍然可用。空白浮层与细缝的共同点是**用户无法判断是坏了还是就这样**，所以要让它自己说话。

**否决的方案**：只加媒体查询的断点、或只调大 `max-height`。
**否决理由**：断点在"媒体查询不成立"的设备上等于没写；`max-height` 管的是上限，管不了"内容为空导致的下限"。

**否决的方案**：让用户强制刷新拿到新 CSS。
**否决理由**：这正是"坏得安静"的那类事故——用户看不出需要刷新；手机客户端里刷新的入口也不总是可见。

**否决的方案**：用 User-Agent 判断手机。
**否决理由**：UA 可伪装，也分不清触屏平板；`pointer: coarse` 与宽度是浏览器自己报的事实。

**否决的方案**：只在 `openOverlay` 里补占位，不量高度。
**否决理由**：不量就不知道"太扁"是否发生，用户回报时也给不出数字。

**后果**：正面——手机上两种失败模式（样式没生效、内容为空）都变成"看得见、说得清"。负面——`body` 上多了一个与本扩展相关的类名，理论上可能与别的扩展冲突；`.ilb-mobile` 与媒体查询两份规则必须同步维护，改一处要改两处（§6.17.1 已写明）。

## D-0035 · 2026-10-24 · "绝不能失效"的几何必须内联写死，兜底也要有高度下限

**背景**：v0.4.6 加了两把钥匙与薄条自愈后，用户仍报"只有很薄一排"，并贴出了那层浮层的 DOM：`.ilb-overlay` 与 `.ilb-modal` 上都带着整串 `style="position: fixed; inset: 0px; display: flex; …"`。那串内联样式就是当时 `ensureVisible` 的兜底产物——它证明**运行时确实走到了"样式没生效"这条分支**，同时暴露了兜底自己的漏洞：兜底只补了位置和背景，**没补 `min-height`**，于是"兜底"把用户送回了"一条缝"。

**决定**：

1. `openOverlay` 在把浮层插进 `document.body` 之后，立刻内联写四条几何：浮层 `position: fixed`、`inset: 0`、`display: flex`、`z-index: 2147483000`；以及弹窗 `min-height`（手机 `45vh`、电脑 `160px`）。观感（圆角、边框、间距、贴底）仍交给 `style.css`，内联的只有"一旦失效就看不见"的那几条。
2. 兜底的 `cssText` 按当前布局生成，并且**必然包含高度下限**；同时把命中的原因写进 warn（`display=none` / `visibility=hidden` / `position=static` / `宽 Npx` / `高 Npx`）。
3. 自愈回调一开始就检查 `overlay.isConnected`：延迟回调可能在浮层已被关掉后才跑，那时量到的 0×0 与 `static` 是假象，不该触发兜底。
4. 自检必须报数：`.ilb-` 规则条数、弹窗高度、计算出的 `min-height`、手机还是电脑布局（ILB-6.17.8）。

**理由**：媒体查询、旧缓存、主题覆盖、别的扩展抢选择器——这些都不在本扩展的控制范围内，而"浮层能不能被看见"不该依赖它们。内联样式是唯一不会被后加载的样式表改写的层。兜底尤其要保守：**兜底是最后一道防线，它自己塌了就没有下一道了**。

**否决的方案**：继续调 `style.css`（例如再加一个断点、把 `max-height` 调小）。
**否决理由**：用户贴出的内联样式说明当时根本没走到样式表那条路；在一条没被执行的路径上做微调，属于"改错了地方"。

**否决的方案**：只在兜底里补 `min-height`，不加内联几何。
**否决理由**：几何失效时浮层会 `position: static`，插在 `body` 末尾、跟着页面滚，用户同样找不到它。

**否决的方案**：给兜底加"永不生效"的标记，避免重复套。
**否决理由**：兜底本身就是幂等的（同一组声明重复写不会更坏），加标记反而引入新的状态要维护。

**后果**：正面——即使 `style.css` 完全没加载，浮层也能铺满屏幕、弹窗至少有可读高度，用户能看见内容，控制台能看见原因。负面——内联样式优先级高于样式表，若将来想让 CSS 控制 `min-height`（例如按内容自适应）会被内联值挡住，必须先改 `openOverlay`；另外手机 `45vh` 的固定下限在很矮的横屏上会显得空。

## D-0036 · 2026-10-24 · "看得见"要量底色，兜底要准备一套皮肤而不只是位置

**背景**：D-0035 之后用户回报"现在不是一小条了，但是点击按钮后，没有页面弹出，或者单纯没有显示"。几何已经内联钉死，尺寸与位置都对，`ensureVisible` 因此认为"没坏"；可弹窗的**底色、边框、文字色**仍然来自那份没生效的样式表。屏幕上的实际画面是：一层透明的全屏容器里套一个透明的盒子——"在，但看不见"。

**决定**：

1. 可见性检查从"量尺寸"升级为"量三件事"：位置与尺寸、**底色**、正文是否有内容；一项不合格就当作样式没生效。
2. 透明度判定必须解析 `rgb()`/`rgba()` 并检查 alpha，不许比较字符串（`transparent` 与 `rgba(0, 0, 0, 0)` 写法不同）。
3. 兜底从"内联几何"升级为"**内置皮肤**"：浮层半透明黑底与层级；弹窗背景、文字色、边框、圆角、阴影、纵向 flex、高度上下限；标题栏分布与下边框；正文区内边距与滚动；关闭按钮最小可点面积。皮肤用的是宿主主题变量的回退值（`--SmartThemeBlurTintColor` → `#1e1e1e`，`--SmartThemeBodyColor` → `#eaeaea`），所以外观仍然跟着主题走。
4. 触发兜底时 warn 必须写明命中的具体项（例如 `弹窗背景是透明的（rgba(0, 0, 0, 0)）`）；一切正常时用 `console.debug` 留一行"检查通过：弹窗 W×H，背景 …，layout"，便于对比"到底走的是哪条路"。
5. 自检增加两条底色检查，用户贴出来就能区分"没渲染"与"渲染了但看不见"。

**理由**：尺寸是"结构"，底色是"呈现"。只测结构，就会漏掉"元素存在但不可见"这一整类故障——而这类故障在用户视角与"完全没反应"没有区别，却是完全不同的根因。另外，兜底既然是最后一道防线（D-0035），它就必须自己就是完整可用的界面，而不是"结构正确、外观交给别人"。

**否决的方案**：继续只改 `style.css`，相信"补上 `min-height` 就好了"。
**否决理由**：这一轮的证据恰好相反——样式表根本没生效，改它不会有任何变化；用户看到的每个症状都发生在"样式表缺席"的前提下。

**否决的方案**：兜底时只写 `background`，不写文字色与边框。
**否决理由**：《检查原件》那层浮层是深色页面上的深色文字；只补背景会把"透明得看不见"换成"看得见一块板子但字融在里面"，用户仍然会报"没显示"。

**否决的方案**：给 `ensureVisible` 加一个"已兜底"的内联标记，避免重复套皮肤。
**否决理由**：套皮肤是幂等的（同一组声明重复写不会更坏），加标记反而多一份要维护的状态；而用户刷新后标记也会消失，等于没解决问题。

**后果**：正面——即使 `style.css` 完全没加载，任何一层浮层都是完整可用的界面（已用 `tests/nocss-probe.html` 在真实 Chromium 里证明：浮层 `rgba(0, 0, 0, 0.55)`、弹窗 `rgb(30, 30, 30)`、500×314、正文与关闭按钮都在）。负面——皮肤里写死了回退色，将来主题变量改名时要同步改两处（`style.css` 与 `applySkin`）；另外 `getComputedStyle` 在极旧 WebView 上的行为未实测，目前只做了"函数不存在就跳过"的防御。

## D-0037 · 2026-10-24 · 手机不再共用电脑那套 UI，改成独立外壳（换路，而不是再补一条兜底）

**背景**：用户（m00002）报"竖屏或手机比例之下，会出现 UI 在点击按钮后无法显示"，并明确指出 v0.4.2–v0.4.8 的四轮修补都没解决。那四轮（D-0030 到 D-0036）做的是同一件事：**让同一套 DOM 在手机上变成另一个形状**——媒体查询、`body.ilb-mobile` 第二把钥匙、内联几何、内置皮肤。每轮都在"用户报症状 → 猜一个成因 → 加一层兜底"里循环，没有一次拿到真机证据。

这一轮先补证据：在合成环境里（真实 `style.css` + 真实模块 + 500×749 手机布局）量到的一切都正常——FAB 52×52、浮窗 500×749 `display=flex z=4500`、帮助浮层 500×749 `z=2147483000`、弹窗 500×410 底色 `rgb(30, 30, 30)`、`elementFromPoint(中心)` 命中弹窗标题、0 错误。**故障在可控环境里无法复现**，说明根因不在几何计算，而在"同一套 DOM 进入真机环境后被改形"这条路（WebView 按桌面宽排版、宿主样式覆盖、触摸事件被手势取消、top layer 被别的层压住，任一都足以）。

**决定**：

1. 手机与电脑拆成**两套独立外壳、共用一个面板**：电脑保留 `ui/floating.js`（悬浮球 + 可拖动浮窗）+ `ui/help.js`（`.ilb-overlay` 浮层）；手机新建 `ui/mobile.js`（悬浮球 + 整屏 `<dialog>` + 二级页栈）。挑哪套、何时切换只在 `ui/shell.js`；`ui/panel.js` 与五个视图不认识外壳。
2. 手机壳必须用原生 `<dialog>` + `showModal()`：它在浏览器 **top layer**，不受任何祖先的 `overflow`/`transform`/`z-index`/`filter` 影响。Z-index 排序、让开、遮罩这些"猜谁在上面"的手段在手机侧整体作废。
3. 手机样式由 `ui/mobile-skin.js` 自带（注入 `<style id="ilb-mobile-skin">`，`.ilb-m` 前缀），**不依赖 `style.css` 是否加载**。手机不再需要媒体查询，也不需要 `body` 上的类。
4. 手机只认 `click`：悬浮球与按钮不得靠 `pointerdown`/`pointerup` 配对判定"点了一下"。
5. 手机上所有次级菜单仍走 `ui/help.js` 的 `openOverlay()`，由 `setOverlayBackend()` 转给手机壳，压进二级页栈；每层有「×」与「←」，热区 ≥44×44；返回键/`cancel` 先关栈顶。
6. 手机上不能用宿主 toastr（它在 top layer 下面）：由外壳提供 `toast()`，界面开着时画在界面里。
7. 电脑那套只服务电脑：`ui/help.js` 不再读"是否手机"，`style.css` 里手机分支（贴底整宽、`.ilb-mobile`、`.ilb-window-mobile`、`.ilb-fab-hidden`、`.ilb-backdrop`、`body.ilb-locked`）**整段删除**，不留"以防万一"的副本。

**理由**：四轮修补的失败模式是同一种——改动的作用面横跨两套环境，而验证只在一套环境里做。换壳把作用面切成两半：手机侧的可见性由 top layer 与自带样式保证（这两件事是浏览器语义，不是推断），电脑侧回到 v0.4.5 之前那套已经被用户确认可用的行为。同时，手机不再继承任何一个历史兜底，坏也只坏在一处。

**否决的方案**：继续在共用 DOM 上补第五条兜底（例如"检测到 WebView 就用内联样式重画整屏"）。
**否决理由**：那本质上是在 JS 里手写第二套界面——既然终点是"重画一套"，不如把它做成真正的独立模块：可读、可测、可单独删除；而继续堆在 `floating.js` 里，下一次故障仍然要同时考虑两套环境的交互。

**否决的方案**：手机也用 `position: fixed` 的全屏 div + 极高 z-index（不换 `<dialog>`）。
**否决理由**：这正是 v0.4.2–v0.4.8 已经证伪的那条路。`z-index` 再高也压不过 top layer、也躲不开祖先的 `transform`/`filter` 建立的包含块；而 `elementFromPoint` 的自检只能事后报警，不能保证可见。

**否决的方案**：保留 `style.css` 里的手机分支，靠"反正手机不走这套"来避免冲突。
**否决理由**：`.ilb-window-mobile` 之类的规则会继续命中电脑侧可能存在的同名类，而 `body.ilb-overlay-open` 那套让开规则一旦与 top layer 叠加，会让"看不见"更难排查。删除比共存便宜。

**后果**：正面——手机界面的可见性不再依赖任何推断（top layer + 自带样式 + 只认 click），375/500 视口在真实 Chromium 里四轮全 PASS，且**不加载 `style.css`** 那一轮同样全过；电脑侧行为不变（`browser-probe` PASS、自检非预期失败 0）。负面——多了一套要维护的界面（两份壳、两份样式词汇），手机的观感与电脑会逐渐分叉；另外 `showModal()` 与宿主既有模态的叠加、安卓返回键是否走 `cancel`、软键盘弹出时的 `visualViewport` 行为，都只有桌面窄视口的证据，真机未验。

## D-0038 · 2026-10-24 · 手机界面的开关只认 `click`，不用 pointer 配对

**背景**：旧悬浮球的"点一下"实现是 `pointerdown` → `pointermove` 超过 5px 记为拖动 → `pointerup` 时 `moved ? 保存位置 : 开合`，代码里还留着一条注释"不要再加 click，否则一次点击开关两次"。这套写法在桌面上没问题，但它把"是否点了一下"押在两件事上：`pointerup` 一定会到达，且浏览器不会在中间取消指针流。手机 WebView 里这两件事都不保证——滚动手势、长按菜单、系统边缘手势都会触发 `pointercancel`，此时 `pointerup` 永不发生，用户看到的就是"点了没反应"。

**决定**：

1. 手机外壳的悬浮球、按钮、二级页关闭一律用 `click` 监听，不读 `pointerup`。
2. 手机不做拖动（整屏界面，没有可拖的东西），因此也不需要"位移阈值区分点击与拖动"这套机制。
3. 电脑那套继续保留 pointer 拖动（它需要把"拖窗口"和"点一下开关"分开），但它的开合仍以 `pointerup` 时的位移判定为准——**这条差异是刻意的**：桌面没有手势取消，手机有。
4. `dialog` 的 `cancel` 事件（Esc / 安卓返回键）必须接管：栈里有二级页就关栈顶，栈空才关整屏；`click` 落在 `dialog` 自身（遮罩区）时同样先关栈顶。

**理由**：`click` 是浏览器在"一次完整的按下-抬起"之后合成的事件，它已经处理了取消、滚动、长按这些情况；pointer 事件是"原始流"，取消语义要自己处理。凡是"点一下做某事"的语义，都应该用已经合成好的 `click`；只有"需要跟随手指"的交互（拖动、滑动）才该用 pointer。手机侧没有拖动需求，用 pointer 只会多出一类失败。

**否决的方案**：pointer + click 双保险（pointer 里判拖动、click 里判开合），靠一个时间戳去重。
**否决理由**：去重逻辑本身又是一个要维护的状态（时间窗设多少？快速连点怎么办？），而且两条路径都要各自正确才不出错；既然手机不需要拖动，直接把指针流整条去掉更简单。

**否决的方案**：给 `pointerup` 加 `pointercancel` 兜底，取消时也当成"点了一下"。
**否决理由**：`pointercancel` 恰恰是"用户不是想点这里"的信号（比如他在滚页面），把它当点击会造成误触；正确的做法是让浏览器自己判定完再给 `click`。

**后果**：正面——手机上"点了没反应"这一整类（指针流被取消）从根上消失；代码里少一套阈值与状态。负面——电脑与手机的开关路径不同，两套壳不能共用同一个"点按"实现；若将来手机也需要拖动，必须重新引入 pointer 并单独处理取消语义。

**否决理由**：叙事引擎要改数据模型与注入时机，一旦中途发现方向不对，回退要拆装配、拆 UI、拆存储；而 `main` 刚发布，用户手上的版本不该被实验拖动。

**否决的方案**：单独建一个仓库放叙事引擎。
**否决理由**：用户说的"模块化"指的是代码分层与可开关，不是拆仓库；两处代码同步会立刻变成负担，将来合并还要跨仓库搬历史。

## D-0040 · 2026-10-24 · 叙事引擎的四条设计纪律（正交原语 / 派生不存 / 原子拒绝 / 有界）

**背景**：这套纪律在 `lab/` 阶段就已按讨论（m00656–m00670）落地，`schema.js` 的注释直接引用了 "D-0040"，但当时没有正式编号。v0.6.0 合并时补写，避免文档里出现悬空引用。

**决定**：

1. **正交原语**：类型六种（text/number/flag/list/map/enum）、约束五种（max/sumMax/range/mutex/require）、效果九种（add/remove/set/inc/dec/mapInc/mark/unmark/reject）、动词八个。新玩法只写声明，不改核心——六种玩法（背包 8 格、负重 20、互斥、冷却、关系表、任务状态机）是这条纪律的验收。
2. **派生不存储**：剩余格、总重量、是否满、关系条目数一律由 `derive()` 现算。存下来就会和列表不一致，而且重放时无法解释。
3. **原子拒绝且可见**：一条事实要么整条生效，要么完全不变；拒绝必须带原因；解析不出的标记进 `unknowns`（带原文与建议），由界面显示。静默跳过是最难查的一类故障。
4. **有界**：规则只做"匹配 + 有限效果"，不做循环与递归；聚合用内置的 count/sum/any/all；表达不了的（排序取最优、配方组合爆炸）留给明确标记的脚本钩子，默认路径永远是可静态检查的声明。

**理由**：涌现应当来自原语的组合，而不是不断加功能；派生值一旦落盘就必然漂移；失败必须出声（ILB-6.15）；无界规则会让一次生成卡死，且用户无法推理。

**否决的方案**：把"剩余格数"做成一个计数器变量。**否决理由**：它会与列表长度漂移，而且重放时无法判断该信任哪个；用户写 `-=1` 之后一次滑动就会多扣。

**否决的方案**：允许规则里写任意 JS 片段。**否决理由**：不可移植、手机上可能失效、无法静态检查，且会绕开原子语义。

**后果**：正面——六种玩法零代码表达、声明错误在编译期可见、规则顺序不影响语义。负面——最优选择、配方组合这类策略目前表达不了，只能等脚本钩子。

## D-0043 · 定位回调：它是记忆账本，不是事件驱动器（v0.7.1，文档修订）

**背景**：v0.7.0 之后用户指出方向偏了——这一模块原本要做的是"总结 / 记录 / 确定角色状态"，
不是做一套玩法引擎；而且深度不该来自事件级联或可视化编程，而该来自"与已有条目、规则、UI 的组合"。
用户同时承认自己前期把"游戏"和"叙事记忆"混在了一起。

**决定（用户明确、可执行）**：
1. **产品定位**：ILB 叙事模块 = **确定性的状态账本**。它只做四件事：从文本里认出承诺（事实标记）、
   用用户声明的约束把它们变确定、把确定的状态注入给模型、把状态开放给条目/规则/界面读写。
   **不是**事件驱动器，**不是**玩法引擎，**不是**游戏。
2. **不做事件级联**：不引入 emit、事件队列、深度/循环调度、节点图。删除 v0.8 的"事件图"路线。
   一次消息仍然只做一次确定性应用（外加每消息一次 tick），失败整条拒绝并出声。
3. **不做玩法模板**：预设只是"示例"，不是产品的一部分；用户按自己的对话场景写少量规则，
   不预设世界、不预设剧情。
4. **组合优先**：复杂来自"条目触发逻辑（触发词/概率/分组/时效）× 状态条件 × 状态写入 × UI 修正"的
   组合，而不是来自新引擎原语。
5. **可视化编辑器后置/不做**：在组合面稳定之前不做图形编程；JSON 编辑 + 给 AI 的编写说明足够。

**保留**：事实解析、六类型/五约束、原子拒绝、重放与检查点、消息块、注入、"叙事"页、声明 JSON 编辑、
v0.7 的自定义状态操作（见下）——它们是"记忆"本身需要的。

**降级/改名**：v0.7 的 events 与"自定义事件"保留代码，但语义降为**自定义状态操作**：
它只是给"某类状态变化"起个名字，由规则映射到状态；不发出事件、不排队、不级联。
文档与界面措辞统一改为"状态操作/状态规则"，不再用"事件驱动器"的说法。

**否决**：
- 事件图 / 调度器 / Blueprint：与"确定性记忆"目标冲突，且无法解释"为什么状态变了"。
- 可视化编程（Scratch/节点图）：在组合面稳定前做，只会把错误模型画得更漂亮。
- 让 AI 自由决定状态：这正是要消除的"口胡"。

**代价**：表达力比"图灵完备的引擎"窄；不能做"中毒→死亡→掉落"这类级联。接受这个代价——
级联可以留给宿主脚本或未来独立模块，不混进记忆层。

**待定（下一步要定的）**：
1. 派生状态（只读计算，如负重、重伤阈值）与"手动修正"哪个先做；
2. 条目侧写入：条目激活时"声明式地"应用事实（entry hook），还是只允许正文标记；
3. 手动修正的形态：直接改状态值，还是只允许"补记/撤销一条事实"（带审计记录）。

## D-0045 · 激活级联用广度优先、字段复用变量表（v0.8.1，2026-10-24）

- **背景**：v0.8.0 的「激活条目」只能拉一层；玩家要的"抽卡"至少要两层（抽卡条目 → 卡池条目）。同时状态页只能手动加变量，条目自己没法提供"可改的字段"。
- **决定一：级联＝广度优先，深度由 `maxActivateDepth` 限（默认 2、上限 5、0 关闭）**。
  - 只处理上一层新激活的条目，同一 id 一轮只激活一次；不拿新条目正文重新做关键词匹配。
  - 为什么不复用触发连锁（`maxChainDepth`）：触发连锁的语义是"文本里提到了什么"，级联的语义是"流程点名要什么"。把两者混在一个深度里，调一个会悄悄改另一个，诊断也说不清是谁带出来的。
  - 为什么不做无限递归：LLM 聊天没有"收敛"保证，A→B→A 一旦漏掉去重就会卡死生成；上限是给用户的保险丝，不是优化。
- **决定二：动态条目字段不建新存储，字段 key 就是聊天变量名**。
  - `withFieldDefaults` 只在判定前补空缺，已有值不动；删掉字段声明，值仍在。
  - 否决"给每条条目单独存一份字段值（entryId → values）"：那会多一张表、多一次迁移，而且流程图和宏要写两套读取路径；变量表已经解决了"同一张聊天内可读可写、换聊天隔离"。
- **代价**：不同条目声明同名字段会共享同一个变量（这是特性也是坑，写文档说明）；级联诊断只有行级记录，没有树形图。
- **验收**：单元 127/127、linkcheck 43/43、smoke 0；真实 ST 未测。
