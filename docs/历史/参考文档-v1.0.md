## 1. 五条设计公理（原文）

**A1 · 运行时零依赖原生世界书。** ILB 不得 import `world-info.js` 的任何内部函数，不得读写其内存状态或 `world_names` 绑定，不得监听原生世界书的触发事件来"派生"自己的行为。与原生世界书的唯一合法交互是**导入/导出时的格式转换**。

**A2 · 条件不进 prompt。** 判定逻辑（匹配规则、条件表达式、算术）只存在于 JS 运行时，不以任何文本形式注入上下文。注入的只有**命中条目的 content**。

**A3 · 注入不落盘。** 注入内容只存在于**单次出站请求的副本**中，不写入 `chat` 数组、不写入 `chatMetadata`、不进入后续轮次的上下文。这是"不污染历史"的机械保证，不是靠事后清理。

**A4 · 三层之间只通过窄接口通信。** 数据层不知道逻辑层存在，逻辑层不知道注入层存在。层间传递的只有两个纯数据形状：`EvalRequest` 和 `ActivationResult`（原文此处注"见 §5"，契约实际在 §4.1，属引用错位）。任何层不得跨层直接调用另一层的内部函数。

**A5 · 失败降级为"零注入"，不降级为"报错中断"。** 判定引擎抛异常、词条数据损坏、注入钩子时序异常——任何一种情况下，生成管线必须继续运行，ILB 本轮不注入任何内容，错误写入调试日志。宁可少注入一轮，不可让用户的生成挂掉。

## 3.1 私有 Schema 原文要点

```jsonc
{
  "schema_version": 1, "book_id": "uuid", "name": "string",
  "entries": [{
    "id": "uuid", "title": "string", "content": "string", "enabled": true,
    "match": { "any": [], "all": [], "not": [], "regex": [],
               "secondary": { "logic": "AND_ANY", "keys": [] },
               "window": null },
    "filter": { "probability": 100, "group": null, "weight": 100 },
    "injection": { "position": "before_char", "depth": 4, "role": "system" },
    "condition": null
  }]
}
```

## 4.2 执行顺序原文

```
1. 对每个 enabled 条目：
   a. match.any / all / not / regex 判定
   b. match.secondary 门槛（若 selective 启用）
   c. window（若配置）：在 chatMessages 的窗口范围内重新执行 a/b
2. 对通过 1 的条目：condition 求值（若存在）
3. 对通过 2 的条目：probability 掷骰
4. 对通过 3 的条目：group 互斥筛选（同组保留 weight 最高者）
5. 按 weight 降序排序，应用 ILB 自己的 token 预算截断
```

## 4.3 扩展原语原文（后被废弃）

> AST 求值器只支持：数值/字符串/布尔字面量；变量引用 `entry.<id>.content.length`、`chat.messageCount`、`vars.<name>`；二元运算 `+ - * / == != > >= < <= && ||`；简单函数 `countMatches(text, pattern)`、`includes(text, str)`。节点类型固定枚举，求值器手写，不反射、不动态执行。

## 7. 九个问题（标题 + 原文对策）

- **7.1 注入路径的时序陷阱** → dryRun 探针，检查 prompt 中是否包含已知内容。
- **7.2 `chat` 数组的引用陷阱** → 深拷贝 + `basedOnMessageCount` 校验。
- **7.3 原生世界书的"基线"与 ILB 的"覆盖层"冲突** → 不去重，加 `[ILB]` 分隔标记，UI 明示并列注入。
- **7.4 Token 计数器的选择** → 字符估算（CJK `chars/3.5`，拉丁 `chars/4`），异步回填。
- **7.5 `depth` 与消息角色的交互** → 默认 system，提供 user 回退；检查前后同角色连续消息，必要时合并。
- **7.6 导入时 `constant` 条目的 `key` 为空问题** → 以布尔值为主依据，`constant && key 非空` 时警告。
- **7.7 正则的 ReDoS 风险** → 单条 10ms 预算，或导入时静态拒绝嵌套量词。
- **7.8 多书同时启用时的条目 ID 冲突** → 加 `bookId::` 前缀，或重生成 UUID + 映射表。
- **7.9 设置持久化的 `saveSettingsDebounced` 竞争** → 独立 `settings.json`，只镜像只读摘要。

**原文一句话总结**：数据层只负责"存和搬"，逻辑层只负责"判定并返回列表"，注入层只负责"把 content 塞进单次请求的副本"。层间只传 `EvalRequest` 和 `ActivationResult` 两个纯数据形状，任何一层失败都降级为零注入而不是中断生成。原生世界书只在导入时被读一次，此后运行时永不触碰。
